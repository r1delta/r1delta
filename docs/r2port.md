# R2 map provider

`r2port_provider` is a path-prefix registry. Providers answer normalized relative paths with existence, size, or shared read-all bytes; the registry keeps a bounded, thread-safe LRU and clears it when another map BSP is requested. R1's filesystem is always consulted before the registry.

For client, listen-server, and legacy dedicated modes, `R1OFactory` receives the native `VFileSystem017` and its `IBaseFileSystem` object. The R2 integration hooks the base-filesystem `FileExists`, size-by-name, and `Open` methods. Each calls the original R1 filesystem first and consults the provider only on a miss. Provider opens return shared memory-file handles; the hooked read, close, seek, tell, and size methods handle those while delegating ordinary handles to R1.

Provider materials and textures are answered by the Open hooks, not by the VPK read hook. The R1 VPK read function fills an out-struct that its callers inspect (`*b == -1` means "not in a VPK, try the file system") and ignores the returned pointer, so a memory handle returned from that hook is never used. In client, listen-server, and legacy dedicated modes the provider answers `IBaseFileSystem::Open` (slot 2) and `IFileSystem::Open` (the `pathId` overload, slot 74 of the stock R1 `filesystem_stdio.dll`); R1 loads VTFs through the latter. Because native code must never dereference a provider handle, `InstallR1FileSystemHandleHooks` also wraps every native `FileHandle_t` consumer of `IFileSystem`: `SetBufferSize` (23), `IsOk` (24), `EndOfFile` (25), `ReadLine` (26), `ReadEx` (75), and `IBaseFileSystem::Flush` (8). It verifies the module's build stamp first: stock `filesystem_stdio.dll` (`0x54874230`, image size `0x2116000`) for client and listen, or stock `dedicated.dll` (`0x54874282`, image size `0x23A2000`), which links the identical filesystem code into its own image and uses the same slots (without this the legacy dedicated server dereferenced a provider handle inside `SetBufferSize` and exited right after the first converted model was served); the R1O TFO layout has two more slots before these and is hooked separately. Map BSP/entity requests still use the documented materialization fallback, now the only provider work left in the VPK read hook, so launch-time map validation sees them.

R1O fake-dedicated mode obtains the TFO `VFileSystem017` through `R1OTFOFileSystemInterface`. Its existing TFO filesystem hooks preserve native lookup and established dedicated loose-file and R1 VPK fallbacks; the R2 provider is consulted last. The same provider is registered for `maps/` files and the `vpk/e*.bsp*` map-list query. Hooks on `VFileSystem017` `FindFirst`/`FindNext` (vtable slots 30/31) append package-name entries for allowlisted R2 BSPs after native results. Point existence and size checks use the provider after existing fallbacks.

The map provider is limited to the 20 allowlisted R2-only maps. It reads only the map BSP and five entity files from the matching `englishclient_<map>.bsp.pak000_dir.vpk`; the BSP is downgraded in memory. AI graphs and BSP lump overrides are optional patch-provided files. The provider does not expose R2 `.bsp_lump` files or names that R1 could treat as `_l_<N>.lmp` overrides.
The converter repacks the cubemaps into the BSP using R1 encoding. The provider converts through `R2ConverterOptions()` in `r2_map_provider.cpp`, which spells out the options it relies on: rule 16 on (static prop flag `0x10` is cleared, because R1 reads it as "shadow caster only, not drawn"), rule 17 shadow options off (`csmRebase`, `emptyShadowMeshes`), and world-light flag bit 2 off. The cubemap scale (rule 13) is not set by the provider: it is the converter's own default (4.0; on `mp_wargames` 1/6 gave 0.67 of R1 brightness and 4 gives 0.85). These equal the converter's defaults, so `bspdown.exe <r2.bsp> <out.bsp>` with no flags writes the same bytes as the provider (checked on `mp_glitch`: identical SHA-256). The converter source in `engine/r2port/bspdown` is vendored from `C:\Users\r3muxd\tmp\r2port\bspdown` by `tools/sync-r2port-bspdown.ps1`, which also copies the CLI driver (`main.cpp`, `build_msvc.bat`), `check_bspdown.py` with `frame_check.py`, and `README.txt` (the rule list); only the sources named in `Dll1.vcxproj` are built into `tier0.dll`. Bump `kConvertedBspCacheVersion` whenever the vendored sources or these options change the output.

The R2 material provider starts opening/building the RPak index on a background thread when the filesystem provider is registered, before a map request. A cold index logs that its first-use build may take several seconds; the completed index is persisted under `<gamedir>/r2port/cache/<R2-install-fingerprint>`, where the fingerprint includes the R2 root and each RPak name, size, and modification time. After map prefetch identifies material and texture paths, the provider records them in a read-mostly hash table protected by a shared mutex; unknown names return a miss without touching the RPak index or conversion queue. Known-path opens wait for the asset conversion (up to 60 s): a missed open leaves R1 with its error texture for the rest of the map, so a miss is never returned for a name the prefetch queued. A VMT's textures are registered as known before its reader resumes. Converted files are persisted under `<cache>/converted/<revision>/materials/...` (VMTs with a `.deps` sidecar listing their textures); the worker loads from there before converting and writes new output through a temporary name plus rename, so a warm map load reads files instead of running r2tex. Bump `kConvertedCacheRevision` in `r2_material_provider.cpp` when the r2tex library or its output changes; deleting the `converted` directory is always safe.

After the converted BSP is served, the provider queues BSP material-name parsing and VMT/VTF conversion on a worker pool capped at four threads, with a one-worker minimum and `cores - 2` workers when that is between one and four. Its queue is capped at 8192 jobs and generated-file LRU at 16 MiB; the decoded RPak family cache defaults to 256 MiB and is configurable with `r2port_tex_cache_mb`. R1 remains first and the provider does not activate for stock R1 maps. Startup, index, callback, conversion, and signon timings, plus material/texture provider hits and misses, are logged with steady-clock timestamps; callbacks over 250 ms log a warning.

Load time (measured in `C:\Users\r3muxd\tmp\r2port\loadprof\RESULTS.md`): text serialization and parsing (emitting a VMT, rewriting entity text, R1's KeyValues parse) is under 0.01 s per map; the time goes into RTech-decoding whole R2 package families. Three mechanisms keep that down.

- Family-grouped dispatch (`r2_family_queue.h`). A worker claims one package family (asset index lookup through `r2tex::FamilyOfMaterial` / `FamilyOfTexture`), drains every queued item of it, and only then takes another; no family is claimed by two workers and at most four families are claimed at a time (`R2PORT_ACTIVE_FAMILIES` overrides; each claimed family is hundreds of MiB decoded), so a family is decoded once per map load instead of once per worker that happens to need it. Blocked readers go first and may claim past the limit by two families. Items already in the disk cache, or whose family does not resolve, need no decode and are dispatched freely. `R2PORT_LEGACY_SCHEDULING=1` restores arrival-order dispatch (A/B baseline). The `R2 texture timing` line gains `family-claims`, `family-loads`, `family-load-ms` (r2tex's own count of decoded families) and `family-active-limit`.
- Parallel index build. A cold RPak index scans package families on `clamp(cores/4, 2, 6)` threads and merges in family order; the file is written in (type, guid) order, so the index is byte-identical to the sequential scan. `R2TEX_INDEX_THREADS` overrides (1 = sequential).
- Converted-BSP cache. `<gamedir>/r2port/bsp_cache/<map>-<fingerprint>.r2bsp` holds the bspdown output (before the lump-0 entity rewrite and the physics patch, which run on every load) plus the SHA-256 of the R2 source BSP that patch sources match against. The fingerprint is `MapPackageFingerprint` (directory VPK and chunk names, sizes and mtimes, `entity_rewrite::kRewriteVersion`, `kConvertedBspCacheVersion`), so bumping `kConvertedBspCacheVersion` when bspdown output changes is what invalidates it; a hit skips the VPK read, the SHA-256 and bspdown. The source-BSP SHA-256 uses CNG (about 70 ms for 150 MB against 520 ms for `p2p::Sha256`). `R2PORT_BSP_CACHE=0` disables the cache; `R2PORT_LOG_HASHES=1` logs the SHA-256 of the served BSP.

The VPK hook checks the provider's read-mostly name index before issuing its extra native filesystem existence probe, so unrelated misses do not trigger another disk lookup. `R1DELTA_R2PORT_TRACE_MISSES` accepts one or more comma-, semicolon-, or pipe-separated path substrings; it records aggregate counts for all material requests and tracks paths only when they match. `R1DELTA_R2PORT_TRACE_FS` uses the same path-substring filter and records up to 4096 matching filesystem calls in a bounded ring without per-call logging. Values such as `0`, `1`, `false`, `true`, `all`, and `*` do not enable tracing. Run `r2port_dump_stats` to print provider counters and write the captured trace to `<gamedir>/r2port/fs-trace.txt` (the ring holds more entries than the console keeps); normal runs leave both traces disabled. The VPK hook no longer handles `materials/` paths at all; the Open hooks trace as `IFileSystem::Open[...]` and `CBaseFileSystem::Open[...]`.

Diagnostic switch: the environment variable `R1DELTA_R2PORT_NO_MODELS=1` makes the model provider register nothing, so no R2 models are served (maps then show R1's error models where R2 models were needed). It exists for A/B crash triage and is read once at startup.

Foliage cavity bake: R2 alpha-tested foliage (shader sets with `Cav` and `Cut`, vertex-lit variant, no `Vcolt`, no AO map in slot 11: grass, ground plants, bushes, leaf cards; 27 materials over the 20 maps, e.g. `world/glitch/glitch_amber_grass_01`) carries a cavity map in slot 12 (a tuft bake, dark roots and light tips). There is no per-vertex or per-instance colour on mp_glitch grass (no VVC, sprp diffuse 255,255,255,255 on all 14,138 blades, constant buffer tint 1,1,1,1); the R2 look (dark green lawn) is R2's cavity occlusion plus the map's colour-correction LUT acting on the resulting dark pixels. `ConvertMaterial` therefore names slot 0 `r2tex/opamerge/<albedo guid>_<opacity guid or 0>_<cavity guid>` and the texture becomes RGBA8 albedo * cavity^k (k = 1.5, env `R2TEX_FOLIAGE_CAV`, `0` disables the bake) with the opacity map (if any) merged into alpha. The mip chain is rebuilt from mip 0 with premultiplied box filtering and an alpha gain that keeps the share of texels at or above `$alphaTestReference` 0.7 constant (R2 draws the cut-out with alpha-to-coverage, whose coverage is the mean alpha at every mip; R1's alpha test lost blades with each mip: 28 % at mip 0, 9 % at mip 4 on the amber grass). mp_glitch, 10 grass-dominated spots, grass pixels conv/R2 luminance median 1.78 -> 1.06, R/G 1.14 -> 1.05, B/G 1.26 -> 1.06; prop class median 1.55 -> 1.34.

Diagnostic converter variants: the environment variable `R1DELTA_R2PORT_BSPDOWN` is a comma separated list that flips one converter option per token for A/B runs without a rebuild: `csm-rebase`, `empty-shadow-meshes` (rule 17), `no-sun-alpha` (rule 21), `no-rtl` and `no-collapse-envs` (rule 20), `pbr-keep`, `flag2`, `props-keep10`, plus `key=value` tokens `sky-scale=<f>`, `sun-scale=<f>`, `pbr-scale=<f>` (rule 20 sky ambient, sun and PBR light multipliers) and `cube-scale=<f>` (rule 13 cubemap scale); the value must be a finite number >= 0. Unknown tokens and bad values are logged and ignored. Defaults chosen by in-game measurement against R2 frames: rule 20 sky ambient scale `skyAmbientScale` = 0.45 (sun and PBR scales 1.0; the unscaled sky ambient left blue shadows on the ground), and model (VertexLitGeneric) materials get `$envmaptint` 0.25 from r2tex (`R2TEX_MODEL_ENVTINT` overrides, read by the converting process; world materials keep 1). The raw string is part of the converted-BSP cache fingerprint, so variants never share a cache file. Unset gives the defaults of `R2ConverterOptions()`.

Rule 20 light limit (crash found 2026-10-27): the R1 client (`sub_1800FCE60`, run once per map load over the world lights) fills a 256-entry table for every light with flag `0x8` and without `0x10` and then copies it into a static 512 byte array that sits right before the client's ConVar objects. A light with flag `0x8` at GPU slot 255 or higher overruns it and corrupts a ConVar (mp_glitch crashed at signon when a script looked up a persistent-data cvar whose name hash collided with the damaged one). bspdown clears flag `0x8` on every point or spot light at array index 255 or higher, and `check_bspdown.py` verifies it.

`<gamedir>/r2port/patches` may contain `<map>.r2patch` physics patches and `<map>.ain.r2patch` AI-graph packages. Both are keyed to the SHA-256 of the source R2 BSP (`maps/<map>.bsp` exactly as read from the map's directory VPK), which no converter or entity-rewrite change alters, so they survive converter updates. Physics patches replace lump `0x1D` only when that hash matches. An AI-graph package (format version 2, written by `tools/pack-r2port-ain.py pack --map M --ain M.ain --source-bsp M.bsp --out M.ain.r2patch`; the tool refuses anything but a version 37 rBSP) is served as `maps/graphs/<map>.ain` when its header hash matches, its map name matches, its body parses as a v54 graph, and `developer` is 0. The provider rebuilds the 12-byte `.ain` header from the live map version and a zero CRC, because the developer-mode entity CRC path (info_node, info_hint, traverse and trigger_indoor_area text) is not reproduced; with `developer` above 0 no package is served. Format version 1 packages (keyed to the converted BSP) are ignored and must be repacked. Missing, malformed, or mismatched packages fall back to the converter's physics stub and no AI graph.

When the engine's VPK read path reports a miss before an ordinary filesystem open, the provider writes only that requested BSP or entity file to `<gamedir>/r2port_cache/<map>-<fingerprint>/maps/` and adds the fingerprinted directory as a tail `GAME` search path, after R1 paths. The fingerprint is SHA-256 over the matching R2 directory VPK and chunk-file names, sizes, and modification times, plus `entity_rewrite::kRewriteVersion` and the provider's `kConvertedBspCacheVersion`, so a change to the entity rules or the converter rebuilds the cache. Writing a new fingerprint directory removes the older `<map>-<fingerprint>` directories of the same map. Before materializing, the hook checks the original R1 filesystem so existing R1 files continue to win. The cache stays under `<gamedir>` because the engine mounts it as a `GAME` search path; it contains only generated BSP and entity files (already rewritten as described above) and is removable with `r2port_clear_cache`. Converter and entity-rewrite changes do not affect the `.r2patch` and `.ain.r2patch` packages, which are keyed to the source R2 BSP.

The R1 map-pack material provider (`r1_map_pack_material_provider.cpp`) is registered after the R2 provider for `materials/`. A background thread indexes every `*client_mp_*.bsp.pak000_dir.vpk` in `<cwd>/vpk` (not `client_mp_common`). A request that R1's own lookup missed and the R2 provider could not answer is read from the pack that holds it, for example `materials/cable/zipline.vmt` (R1 forces it for ropes; served from `englishclient_mp_airbase`) and `materials/tools/toolsskybox.vmt`. R1 content always wins, and the first served zipline or skybox file is logged once.

The R2 model provider (`r2_model_provider.cpp`, converter vendored under `engine/r2port/modelconv` by `tools/sync-r2port-modelconv.ps1`) answers `models/**.mdl`, `.vvd`, `.dx11.vtx`, `.vtx`, `.phy` and `.vvc` for the 20 allowlisted maps. R2 models are MDL v53 files with embedded companions inside `englishclient_<map>.bsp.pak000_dir.vpk` and `englishclient_mp_common.bsp.pak000_dir.vpk`; the converter turns them into R1 MDL v52 plus companions. A model whose `.mdl` R1 already has (checked with the native existence probe) is never served from R2, including its companions, because a converted R2 VVC or PHY next to an R1 MDL crashes the client. The converted R1 MDL always has the `@ref` animation and the `ref` sequence as sequence 0 (client-side animating entities (`prop_dynamic`) index sequence 0 unconditionally and crashed in `client.dll+0x104DC` when the converter dropped them), and `ref` carries the pose of the R2 reference animation instead of the bone bind pose (the bind pose draws `escape_pod` on its side and `mobile_hardpoint` collapsed). Every other R2 sequence that plays exactly one animation is converted to R1 animation data (position, rotation and scale tracks, raw and delta records), so `prop_dynamic` `DefaultAnim` names such as the `imc_fan_large_01_animated` `fast_spin` run in game. Sequences that blend several animations (pose parameters), have auto layers, IK rules or locks, animations with local hierarchy, IK rules or the frame-anim layout or with invalid data, and position tracks that need a coarser shared scale than one R1 bone holds are dropped one by one; movement data is discarded; a model whose animation data cannot be converted at all falls back to the one-frame bind-pose output. Conversions are cached per root in `<gamedir>/r2port/cache/models/<revision>/<package signature>/` (bump `kModelCacheRevision` when the converter changes; revision 6 is the first with converted animations). When the BSP is served, a background thread converts every model named in the converted BSP's `sprp` lump and in the five entity files, and registers each model's materials with the material provider as known paths (`PrefetchR2ModelMaterials`); the MDL read registers them again, so a material is known before R1 resolves it. Known paths whose VMT or textures were cached from an earlier map are re-registered after a map change. `r2port_dump_stats` prints the model counters.

Converted models rename every material into the `r2m/` namespace (the converter prefixes each texture directory with `r2m\`, adding one when the MDL has none; `ListModelMaterials` returns the `r2m/` names). The material provider converts `materials/r2m/<R2 material>.vmt` with r2tex like any other material and rewrites a `LightmappedGeneric` shader line to `VertexLitGeneric`. Reason: R2 models reference materials whose R2 shader is a world shader (518 of the 1300 model material references in homestead, eden and colony02). R1 handles those on static props, but on entities (`prop_dynamic`, `script_mover` models such as the homestead water wheels) studiorender draws a mesh with a lightmapped material and materialsystem_dx11 indexes its cubemap SRV table (`unk_180292608`, 32 entries bound to PS slot 9) with an invalid index, crashing in `d3d11!SetShaderResources` (`studiorender+0x1855c` -> `materialsystem_dx11+0x628d4`). It reproduced on mp_homestead within seconds of spawn with only the water wheel models served, and not with `R1DELTA_R2PORT_NO_MODELS=1`. The namespace also keeps the world material of the same name unchanged.

`R2MapPackFileProvider` (in `r2_map_provider.cpp`, registered for `materials/` after the other providers) serves `.vtf`, `.vmt` and `.raw` files that the active R2 map's own directory VPK carries and nothing else answers: the `cloudmask` textures and `color_correction` `.raw` files that only entity keys name (present in all 20 maps' VPKs), plus a few map-specific VMT and VTF files.

## Particles

R2 particle systems are PCF files (`particles/*.pcf`, DMX binary 5 / pcf 2, the same container as R1) inside `englishclient_frontend.bsp.pak000_dir.vpk`. `engine/r2port/particles` (vendored from `C:\Users\r3muxd\tmp\r2port\particles` by `tools/sync-r2port-particles.ps1`) converts the systems the 20 allowlisted maps place with `effect_name` entities, plus everything they reference as children, into one R1 PCF: every system is renamed `r2p_<name>` (so R1's own definitions are never replaced), GUIDs are regenerated, functions R1's client does not implement are dropped (`render_scripts`, `Follow Projectile Arc`, `Sound Meter Scalar`, and `emit_instantaneously by distance`, which becomes a fixed `emit_instantaneously` burst only when the system has no other one), and R2-only attributes are removed. The request list (`r2_particle_requests.inc`, 79 systems; 12 more effect names are identical in R1 and are left alone) and the supported-function list (`pcfconv_tables.inc`) are generated by `tools/gen_tables.py` in the converter directory.

`r2_particle_provider.cpp` serves the result as `particles/r2port.pcf`, built in memory on first use (about 60 ms; no disk cache, so there is no cache revision beyond `entity_rewrite::kRewriteVersion`), and serves R2-only `materials/particle/**` VMT/VTF files from `englishclient_mp_common.bsp.pak000_dir.vpk` (map-specific ones come from `R2MapPackFileProvider`). R1 reads `particles/particles_manifest.txt` once at client Init, and the provider cannot override that file, so `r2port_particles_hook.cpp` detours client.dll `ParseParticleEffects` (RVA 0x1CD5B0, prologue-checked) and, after the original, calls `ReadParticleConfigFile(*(client+0x380F1F0), "particles/r2port.pcf", 0, 0)`. Without an R2 install nothing is served and the call is skipped. `R1DELTA_R2PORT_NO_PARTICLES=1` disables the provider and the `effect_name` rename (read once at startup) for A/B checks. The log line `R1Delta: R2 particles converted ...` reports the conversion; `R1Delta: R2 particle file particles/r2port.pcf loaded=1` the load.

## Entity rewrite

R2 entity text uses classes and keys that R1 does not know. `engine/r2port/entity_rewrite.{h,cpp}` (library with no engine dependencies; CLI and tests in `tools/r2port`, run `tools/r2port/run_entity_rewrite_tests.cmd`) rewrites it:

| Input | Output |
|---|---|
| `prop_dynamic_lightweight` | classname becomes `prop_dynamic`, all keys kept |
| `script_mover_lightweight` | record dropped (R1 `script_mover` does not take its rotator keys) |
| `light_environment_volume` | record dropped (not the same thing as the global `light_environment`) |
| `mp_eden` `info_target` `targetname "spacenode"` | becomes `intro_SpaceNode`, which `mp_eden.nut` looks up |
| `info_spawnpoint_flag` `teamnumber` | key renamed `TeamNum` when `TeamNum` is absent; R1 CTF reads the flag team from it |
| `info_particle_system`, `prop_dynamic`, `prop_dynamic_lightweight` `effect_name` | renamed to the converted `r2p_<name>` system when the effect is one the particle provider converts (see Particles); other effects keep their name and use R1's own definition |

Everything else is preserved byte for byte (line endings included; a test covers CRLF text and checks that the real `light_environment` block is never dropped, reordered or edited), including `info_target_clientside` (R1's own `mp_mia`/`mp_nest2` use it), `editorclass`/`spawnclass` (never promoted to `classname`), `move_rope` `RopeMaterial "cable/zipline.vmt"` (served by the R1 map-pack material provider), and the keys other providers depend on: `cloudmask`, `cloudoffset`, `color_correction` `filename`. No R2 lightweight network or animation behavior is reproduced. The rewrite is idempotent and fails open: text it cannot parse is served unchanged and logged.

One non-idempotent step runs on lump 0 only, after the rewrite: `RaiseFlagSpawnOrigins` lifts every `info_spawnpoint_flag` origin by `kFlagSpawnLift` (8 units). R2 authors the flags on the floor; the R1 server drops a flag spawnpoint to the floor itself but removes one whose origin starts inside solid, and the converted collision can put the floor a unit above the R2 origin. `mp_lf_stacks` lost its second flag that way (z 0.0006 against a floor at 1.03); with the lift both flags exist in CTF and the spawnpoints settle on the floor as before. `mp_glitch` is unchanged (both flags still end at z 2.03).

The provider applies it in two places: to each of the five partition files (`_env`, `_fx`, `_script`, `_snd`, `_spawn`) as they are read from the R2 package (`Size` and `Read` both report the rewritten bytes; the result is cached per map), and to lump 0 of the converted BSP, where the CTF flag spawnpoints live (the BSP is repacked with the same lump replacement the physics patch uses, so game-lump offsets stay valid, and it is left untouched when no rule matches). Each rewrite that changes a file logs one line, `R1Delta: R2 entity rewrite map=<map> <file|bsp-lump=0> entities=<in>-><out> ...`. Bump `entity_rewrite::kRewriteVersion` whenever the output for the same input changes.

## Titanfall 2 install search

The player's own Titanfall 2 install (its `vpk` and `r2/paks/Win64` rpaks) is found by one search order, implemented twice and kept identical: `TitanfallLocator.FindTitanfall2` in `launcher_ex/TitanfallFinder.cs` and `DiscoverR2Install` in `engine/filesystem/r2_map_provider.cpp`. Change both together.

1. Explicit path. The launcher's `manualPath` argument (a root directory, or a file directly inside it; the launcher has no saved setting yet) and the `R1DELTA_TITANFALL2_PATH` environment variable (the engine has only this one). An explicit choice that does not validate ends the search with no result; it never falls back to another install.
2. `HKLM\SOFTWARE\Respawn\Titanfall2` value `Install Dir`, 64-bit then 32-bit registry view.
3. Uninstall entries under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` (both views) whose key is the EA product GUID `{4BD80373-FEE7-45B6-8249-6E8E98717405}` or `Steam App 1237970`, or whose display name reads Titanfall 2 (`^Titanfall\S{0,3}\s*2\b`, case-insensitive; the EA installer writes a mangled trademark sign): the `InstallLocation` value.
4. Steam. Roots from `HKLM\SOFTWARE\Valve\Steam`, `HKLM\SOFTWARE\WOW6432Node\Valve\Steam` and `HKCU\Software\Valve\Steam` (values `InstallPath`, `SteamPath`), then every library in each root's `steamapps\libraryfolders.vdf` (both the `"path"` and the older numeric-key layouts). In each library: the `installdir` from `appmanifest_1237970.acf`, then `steamapps\common\Titanfall2`, then `steamapps\common\Titanfall 2`.
5. `Titanfall2` and `Titanfall 2` under `\`, `Games`, `Games\EA`, `EA Games`, `Program Files\EA Games`, `Program Files (x86)\Origin Games`, `Program Files (x86)\Steam\steamapps\common` and `SteamLibrary\steamapps\common` on every fixed or removable drive.

Every candidate, whatever its source, must pass the same validator: `bin\x64_retail\rtech_game.dll`, at least one `.rpak` in `r2\paks\Win64`, a `*client_mp_common.bsp.pak000_dir.vpk` and `client_mp_common.bsp.pak000_000.vpk` in `vpk`, and no `r1\gameinfo.txt` (that marks Titanfall or R1Delta, so the Titanfall finder and this one can never accept the same folder). The engine runs the search once, on first use, and logs `R1Delta: R2 map provider install discovery found <path> via <source>` (or that it found none, or that the environment variable is set but not a valid install).

## Shader track

`engine/r2port/shaders` compiles our own HLSL at runtime and lets a converted VMT use it by name. R1's `screenspace_general` material class names its shaders through `$pixshader "<name>"` (file `shaders\fxc\<name>_ps40.vcs`) and `$vertexshader "<name>"` (`<name>_vs40.vcs`). `r2_shader_compiler.cpp` runs `D3DCompile` (`ps_4_0` / `vs_4_0`) and wraps the DXBC as a VCS v6 file with the same layout as the stock files; `r2_shader_cache.cpp` keeps the files under `<gamedir>/r2port/shadercache` (rebuilt when the source hash or `kCacheRevision` changes) and `R1BaseFileSystem_Open` (factory.cpp) opens them by absolute path when R1's own file system misses a `shaders\fxc\...` request. They are real files, not provider memory handles, because the shader loader calls `AllocOptimalReadBuffer` on the handle, which the provider memory handles do not implement. Sources are embedded in `r2_shader_sources.h`; `<gamedir>/r2port/shaders/<name>.hlsl` adds or overrides one without a rebuild. A source that fails to compile or link logs `R1Delta: R2 SHADER BUILD FAILED` with the compiler text and writes no file (the material then does not draw); `r2port_shaders` lists the state and `r2port_shaders_rebuild` recompiles. Offline check: `.build\build-r2-shader-cli.cmd`, then `.build\r2_shader_cli.exe <outdir>`.

Contract learned from the stock default vertex shader `screenspaceeffect_vs40` and from game runs: b0 = the 20 floats `$c0_x..$c4_w`; b2 `CBufCommonPerCamera` and b3 `CBufModelInstance` are bound for the vertex shader; t0..t3/s0..s3 = `$basetexture`, `$texture1..3`; a custom `$vertexshader` is always asked for static combo 0 (the engine only varies the combo for the default VS), so the vertex file is the transformed build and `$vertexshader "<name>_vcol"` selects the vertex-colour build. Verified in game on world brushes (`mp_coliseum`): custom pixel shader with the default vertex shader, and custom vertex plus pixel shader reading b2/b3, UVs, a 2D texture and the view direction. Not working yet: the same materials on the coliseum dome static prop draw nothing. See `r2port/shaderlab/SHADER-TRACK.md`.

Pixel-shader override (`r2_shader_override.cpp`): R1's `UnlitTwoTexture` class fills its draw state (`a4+24` pixel shader name, `a4+72` pixel combo) in the vtable-slot-9 function at materialsystem_dx11 RVA 0x2FA10 (checked against the retail build stamp and prologue). The hook calls the original and, for a material whose `$godrayMinFadeDist` is `7700 + id` (a parameter the class ignores while `$godray` is 0), swaps in our pixel shader from the cache. Props and brushes keep the stock vertex shader, vertex format and draw path, which `screenspace_general` does not do on static props (adding a compressed-normal NORMAL input to the custom vertex shader did not help; cause still unknown). Id 1 is `r2_ut_dome`, a copy of the stock static combo 0x110 (fresnel + `$addlayers`, no fog, dyn 0; disassembled from `unlittwotexture_ps40.vcs`) whose layer 2 is a `TextureCube` at t1 sampled along `TEXCOORD7`; the material must set `$nofog 1` because our file has one dynamic variant. r2tex emits it for `world/test/kodai_fake_screen_01_world`, `skies/boomtowncubemap_grave` and `skies/boomtowncubemap_desert` (default on; `R2TEX_SHADERS=0` restores the scan-line-only VMT). Verified in game on `mp_coliseum` (static prop dome) and `mp_grave`.

LightmappedGeneric override (world brushes, `r2_shader_override.cpp`, `r2_shader_source_lmg.h`, env `R2_LMG_PBR`, default OFF: with the variable unset there is no hook and no LMG shader is compiled). Hook on the class' vtable slot 9 (RVA 0x28610, prologue checked), same idea as above: after the original fills `a4`, an eligible draw gets our pixel file (`r2_lmg_pbr_ps40`) and static combo = index * 12; the stock vertex shader, vertex format and draw path stay. Values: `1` = materials with `$treesway 7701`, `all` = every eligible material, `neutral` / `mark` = validation shaders (stock formulas only / same tinted), `dbg6|7|8` = panel visualisations, `log` or `+log` = write every distinct draw state and reject reason to `<gamedir>/r2port/lmg_log.txt`. Eligible = stock `lightmappedgeneric_ps50` + `_vs40`, real-time-light path on (render flags dword at RVA 0x38FB2C: `& 0x1400000 == 0x400000`, `& 0x2000000 == 0`), a vertex combo with tangents (`(a4+76)/2 % 6` is 2 or 5), `$basetexture`, `$bumpmap`, `$reflectionTint`, no `$vertexcolor`, no godray; single layer, or two layers with `$baseTexture2`, `$bumpmap2`, `$reflectionTint2`, `$blendModulateTexture`. The pixel file holds 5 static combos x 12 dynamic combos (lights / shadow mode / fog flavour exactly like the stock file) because R1 links the vertex and pixel stage by REGISTER: a pixel shader must declare the same register layout as the vertex combo (TEXCOORD1.xy occupies a register when a detail texture is present; TEXCOORD3 is a float4 for two layers). Stock terms were reconstructed from the reflected stock bytecode (lightmap decode, bumped sky weight, CSM PCF with cloud mask, real-time light list from t20, hardware lights, two fog flavours, `c_lightScale`); `neutral` reproduces the stock frame (median pixel difference 0, mean 0.1 to 1 of 255 on three maps, remaining difference is the scene itself). Added R2 terms: GGX-shaped specular driven by gloss, F0 from `$reflectionTint` (re-encoded to the stored value, see PHASE2.md), AO on lightmap, sky and ambient, cavity on specular, and a highlight from the baked light direction (lightmap plane B). Material data reaches the shader packed: single layer `$detailColor` (t4, `$detailColorMode 1`) = r gloss, g AO, b cavity; two layers `$blendModulateTexture` b = gloss layer 1, a = gloss layer 2 plus `$treesway 7701`. r2tex does not emit these yet.

Credit: ficool2's sdk_screenspace_shaders documented the screenspace_general register convention (used with the author's permission); a shader author who provided hints on the Uber material model. No code from either is included.

## Test roots

The user's `S:\game\r2` is their separate play tree; they can launch it directly through `S:\game\r2\r1delta.exe`, with `S:\game\r2\r1delta` beside it. Agents MUST NOT stage, reset, or run tests from it. Agents also do not modify `S:\game\mp` or `S:\game\r1delta`. `S:\game\r2dev` is the golden template and staging reference; agents do not launch tests from it.

Agent roots:

- `r2-provider` for ProviderHook
- `r2-texlib` for TexLib
- `r2-shader` shared by ShaderLab and RootBuilder
- `r2-lead` for the lead

Create, stage, and verify an agent root from the pinned template:

```powershell
powershell -ExecutionPolicy Bypass -File .build\r2-root.ps1 -Create -Root r2-provider -From r2dev
powershell -ExecutionPolicy Bypass -File .build\r2-root.ps1 -Stage -Root r2-provider
powershell -ExecutionPolicy Bypass -File .build\r2-root.ps1 -Verify -Root r2-provider
powershell -ExecutionPolicy Bypass -File .build\r2-root.ps1 -Status -Root r2-provider
```

Use `-Reset -Root <agent-root>` to remove and recreate only that agent root, then run `-Stage` again before launching. Use `-Remove -Root <agent-root>` to delete one agent root safely, `-List` to report all roots, and `-Status -Root <agent-root>` to show its creation time, private payload MiB, shared hardlink MiB, and running process count. Creation is refused when `C:` has less than 3 GiB free. `r2dev` is template-only; `-Create`, `-Reset`, and `-Remove` do not operate on it.

Each launch root has root files hardlinked from `S:\game\mp`, `bin`/`r1`/`tools` junctions like `mp`, and private real `crash`/`crashes` directories. Each CORE is an independent clone pinned to `316993bd0142e706ea5386943530f2b8d2c711dd` with `core.autocrlf=false`; `scripts`, `resource`, and `maps` are private checkouts, while `bin_delta` and staged executables are private copies. Large existing CORE content under `bin`, `materials`, `models`, `sound`, `cfg`, `config`, `admin`, `bin_nexon`, and `vgui` is in real directories whose existing files are hardlinks to the template. Hardlinks share disk blocks and file metadata, not directory entries: agents may add files or unlink their own link, but MUST NOT open an existing hardlinked file for writing. Fixture installers unlink the agent root's file before replacing it and restore the original from `r2dev` on removal. Runtime additions and fixture directories are locally excluded from Git status; tracked files are still checked against pinned Git blobs. `-Verify` checks layout, hardlink identities, sample blob hashes, private write probes, and absence of IDA databases.

`-Stage -Root <agent-root>` updates only that root and refuses while a process is running from the same root; other agent roots may stay active. There is no shared `GAME.lock` or stage/unstage/core-swap flow for agent runs. `-Remove` unlinks hardlinks and removes junctions without following them.

## Background test mode

Agent and CI game windows must not disturb the person using the machine. Setting the environment variable `R1DELTA_BACKGROUND=1` (anything but `0`) or passing `-r1delta_background` turns on a mode that is never active otherwise, so normal players and hand launches are unchanged. `.build\run-in-r2.ps1` sets the variable for every launch it starts and adds `+fps_max 60 -nomessagebox` to the game arguments; a hand-launched agent window needs only the variable or the switch. The code is `engine/core/background_mode.cpp`.

- **Focus and input.** user32 hooks (MinHook, installed with the other early hooks) make `SetForegroundWindow`, `BringWindowToTop`, `SetActiveWindow`, `SetFocus`, `SwitchToThisWindow`, `ClipCursor`, `SetCursorPos`, `SetCapture` and `mouse_event` do nothing, make `SendInput` fail, make `RegisterRawInputDevices` report success without registering (no raw mouse input ever arrives), strip `WS_EX_TOPMOST`/`HWND_TOPMOST` and add `WS_EX_NOACTIVATE`/`SWP_NOACTIVATE` in `CreateWindowEx`, `SetWindowLong(Ptr)` and `SetWindowPos`, and map every `ShowWindow`, `ShowWindowAsync` and `SetWindowPlacement` show command to a non-activating one. `r1d_background_selftest hooks` reports how many are patched (26 of 26 including the message-box hooks).
- **Window placement: off-screen by default.** The window is created at (-32000,-32000) and shown with `SW_SHOWNOACTIVATE`. It keeps its full 1920x1080 size, renders and ticks at 60 fps, `screenshot` works and a `PrintWindow` client grab returns the real frame. `R1DELTA_BACKGROUND_WINDOW=minimized` selects `SW_SHOWMINNOACTIVE` instead; it also renders at 60 fps and the engine `screenshot` works, but a minimized window has a 0x0 client area (a `PrintWindow` grab only gets the 160x28 title bar), and creating the window already minimized crashes graphics initialisation (an allocation fails in the first swapchain-sized buffer), so only the show command is mapped, never the creation style.
- **60 fps.** The command line gets `+fps_max 60 +mat_vsync 0` and a watchdog thread re-applies `fps_max 60` and `mat_vsync 0` every second, so cfg files cannot override them. The engine throttles itself to about 20 fps (a 50 ms sleep per frame) while it believes it is not the active app, which a background window always is; the same thread therefore posts `WM_ACTIVATEAPP` (active) to the game's windows twice a second. Measured with a client script frame counter: 19.4 fps without it, 59.3 to 60 fps with it.
- **Crashes and message boxes.** The crash log is still written to `crashes`, but `notepad.exe` is not started and the crash sounds are not played. `MessageBoxA/W/ExA/ExW` log caption and text (console and debugger output) and return at once (`IDOK`; `IDYES` for yes/no and yes/no/cancel; `IDCANCEL` for retry/cancel; `IDIGNORE` for abort/retry/ignore). `-nomessagebox` has the same suppression in every mode, background or not. `r1d_background_selftest messagebox` and `crash` exercise both; the command is registered only in background mode.
- **Engine switches.** The command line also gets `-nosound -nomouse +cl_mouseenable 0 +cl_mouselook 0` unless already present. Verified on this engine: `-nosound` is honoured (neither `XAudio2_6.dll` nor `MMDevApi.dll` is loaded, which a normal client does load, and map load, spawning and the game state still progress). `-nomouse` cannot be observed from outside; the real guarantees are the hooks above. `cl_mouseenable` and `cl_mouselook` exist but did not change from 1 when set at run time (`cl_mouselook` is flagged not-while-connected), so they are only a best effort; `engine_no_focus_sleep`, `host_framecount`, `snd_mute_losefocus` and `volume` do not exist in this engine.

**Automatic for agent roots.** An empty file `r1delta_background.flag` next to the game executable also turns the mode on, so a launch from an agent root is a background launch whatever script started it and whether or not it sets the environment variable. `.build\r2-root.ps1` creates the flag for the four agent roots (`r2-provider`, `r2-texlib`, `r2-shader`, `r2-lead`) on `-Create`, `-Reset`, `-Repair` and `-Stage`, and never for the template `r2dev` or the user's `S:\game\r2`. Only the executable's directory is checked; the working directory (`C:\whatever` for the runner) is shared and is deliberately not consulted. However the mode is enabled, `-nosound` is applied (no audio DLL is loaded) unless `R1DELTA_BACKGROUND_SOUND=1` is set. A hand-staged root gets the flag by running `-Stage` once, or by creating the empty file.

Evidence for these results (mp_glitch from `S:\game\r2-provider`): the foreground window and its process never became the game's across a full run, the window was never topmost, and the notepad process list did not change on a forced crash.

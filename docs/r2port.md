# R2 map provider

`r2port_provider` is a path-prefix registry. Providers answer normalized relative paths with existence, size, or shared read-all bytes; the registry keeps a bounded, thread-safe LRU and clears it when another map BSP is requested. R1's filesystem is always consulted before the registry.

For client, listen-server, and legacy dedicated modes, `R1OFactory` receives the native `VFileSystem017` and its `IBaseFileSystem` object. The R2 integration hooks the base-filesystem `FileExists`, size-by-name, and `Open` methods. Each calls the original R1 filesystem first and consults the provider only on a miss. Provider opens return shared memory-file handles; the hooked read, close, seek, tell, and size methods handle those while delegating ordinary handles to R1.

Provider materials and textures are answered by the Open hooks, not by the VPK read hook. The R1 VPK read function fills an out-struct that its callers inspect (`*b == -1` means "not in a VPK, try the file system") and ignores the returned pointer, so a memory handle returned from that hook is never used. In client, listen-server, and legacy dedicated modes the provider answers `IBaseFileSystem::Open` (slot 2) and `IFileSystem::Open` (the `pathId` overload, slot 74 of the stock R1 `filesystem_stdio.dll`); R1 loads VTFs through the latter. Because native code must never dereference a provider handle, `InstallR1FileSystemHandleHooks` also wraps every native `FileHandle_t` consumer of `IFileSystem`: `SetBufferSize` (23), `IsOk` (24), `EndOfFile` (25), `ReadLine` (26), `ReadEx` (75), and `IBaseFileSystem::Flush` (8). It verifies the module's build stamp first: stock `filesystem_stdio.dll` (`0x54874230`, image size `0x2116000`) for client and listen, or stock `dedicated.dll` (`0x54874282`, image size `0x23A2000`), which links the identical filesystem code into its own image and uses the same slots (without this the legacy dedicated server dereferenced a provider handle inside `SetBufferSize` and exited right after the first converted model was served); the R1O TFO layout has two more slots before these and is hooked separately. Map BSP/entity requests still use the documented materialization fallback, now the only provider work left in the VPK read hook, so launch-time map validation sees them.

R1O fake-dedicated mode obtains the TFO `VFileSystem017` through `R1OTFOFileSystemInterface`. Its existing TFO filesystem hooks preserve native lookup and established dedicated loose-file and R1 VPK fallbacks; the R2 provider is consulted last. The same provider is registered for `maps/` files and the `vpk/e*.bsp*` map-list query. Hooks on `VFileSystem017` `FindFirst`/`FindNext` (vtable slots 30/31) append package-name entries for allowlisted R2 BSPs after native results. Point existence and size checks use the provider after existing fallbacks.

The map provider is limited to the 20 allowlisted R2-only maps. It reads only the map BSP and five entity files from the matching `englishclient_<map>.bsp.pak000_dir.vpk`; the BSP is downgraded in memory. AI graphs and BSP lump overrides are optional patch-provided files. The provider does not expose R2 `.bsp_lump` files or names that R1 could treat as `_l_<N>.lmp` overrides.
The converter repacks the cubemaps into the BSP using R1 encoding. The provider converts through `R2ConverterOptions()` in `r2_map_provider.cpp`, which spells out the options it relies on: rule 16 on (static prop flag `0x10` is cleared, because R1 reads it as "shadow caster only, not drawn"), rule 17 `csmRebase` on (BSP cache 21: R2's empty dummy CSM environment is dropped, the real environment being chosen by content (largest nodes + refs + meshes, ties later), not as the last record, except `mp_coliseum` and `mp_coliseum_column` (no cloudmask, dummy `light_environment` stays last; `csmLastEnv` / token `csm-last-env`) (BSP cache 24: on mp_black_water_canal, mp_angel_city, mp_coliseum and mp_coliseum_column the dummy is last), so R1's tree root is the real one and tree/prop sun shadows are drawn; object references are bounded by `[0, ((levelinfo word 2 + 63) & ~63) + props)`) with `emptyShadowMeshes` off, rule 13d `cubemaps split` on (per-mesh R2 cubemaps through patch materials), rule 20f `rtlBake` edge on (BSP cache 22: spot/point real-time lights whose shadow edges R1 cannot reproduce are baked into lightmap plane A; opt-out tokens `rtl-bake-none`, `no-rtl`), and world-light flag bit 2 off. The cubemap scale (rule 13) is not set by the provider: it is the converter's own default (4.0; on `mp_wargames` 1/6 gave 0.67 of R1 brightness and 4 gives 0.85). The provider's defaults for `csmRebase`, `cubemaps` and `rtlBake` differ from the library defaults (off, none, 0), so the CLI writes the provider's bytes with `--csm-rebase --cubemaps split --rtl-bake edge` (before BSP cache 21/22 the no-flag CLI equalled the provider on `mp_glitch`: identical SHA-256; not re-checked since). The converter source in `engine/r2port/bspdown` is vendored from `C:\Users\r3muxd\tmp\r2port\bspdown` by `tools/sync-r2port-bspdown.ps1`, which also copies the CLI driver (`main.cpp`, `build_msvc.bat`), `check_bspdown.py` with `frame_check.py`, and `README.txt` (the rule list); only the sources named in `Dll1.vcxproj` are built into `tier0.dll`. Bump `kConvertedBspCacheVersion` whenever the vendored sources or these options change the output.

The R2 material provider starts opening/building the RPak index on a background thread when the filesystem provider is registered, before a map request. A cold index logs that its first-use build may take several seconds; the completed index is persisted under `<gamedir>/r2port/cache/<R2-install-fingerprint>`, where the fingerprint includes the R2 root and each RPak name, size, and modification time. After map prefetch identifies material and texture paths, the provider records them in a read-mostly hash table protected by a shared mutex; unknown names return a miss without touching the RPak index or conversion queue. Known-path opens wait for the asset conversion (up to 60 s): a missed open leaves R1 with its error texture for the rest of the map, so a miss is never returned for a name the prefetch queued. A VMT's textures are registered as known before its reader resumes. Converted files are persisted under `<cache>/converted/<revision>/materials/...` (VMTs with a `.deps` sidecar listing their textures); the worker loads from there before converting and writes new output through a temporary name plus rename, so a warm map load reads files instead of running r2tex. Bump `kConvertedCacheRevision` in `r2_material_provider.cpp` when the r2tex library or its output changes; deleting the `converted` directory is always safe.

After the converted BSP is served, the provider queues BSP material-name parsing and VMT/VTF conversion on a worker pool capped at four threads, with a one-worker minimum and `cores - 2` workers when that is between one and four. Its queue is capped at 8192 jobs and generated-file LRU at 16 MiB; the decoded RPak family cache defaults to 256 MiB and is configurable with `r2port_tex_cache_mb`. R1 remains first and the provider does not activate for stock R1 maps. Startup, index, callback, conversion, and signon timings, plus material/texture provider hits and misses, are logged with steady-clock timestamps; callbacks over 250 ms log a warning.

Load time (measured in `C:\Users\r3muxd\tmp\r2port\loadprof\RESULTS.md`): text serialization and parsing (emitting a VMT, rewriting entity text, R1's KeyValues parse) is under 0.01 s per map; the time goes into RTech-decoding whole R2 package families. Three mechanisms keep that down.

- Family-grouped dispatch (`r2_family_queue.h`). A worker claims one package family (asset index lookup through `r2tex::FamilyOfMaterial` / `FamilyOfTexture`), drains every queued item of it, and only then takes another; no family is claimed by two workers and at most four families are claimed at a time (`R2PORT_ACTIVE_FAMILIES` overrides; each claimed family is hundreds of MiB decoded), so a family is decoded once per map load instead of once per worker that happens to need it. Blocked readers go first and may claim past the limit by two families. Items already in the disk cache, or whose family does not resolve, need no decode and are dispatched freely. `R2PORT_LEGACY_SCHEDULING=1` restores arrival-order dispatch (A/B baseline). The `R2 texture timing` line gains `family-claims`, `family-loads`, `family-load-ms` (r2tex's own count of decoded families) and `family-active-limit`.
- Parallel index build. A cold RPak index scans package families on `clamp(cores/4, 2, 6)` threads and merges in family order; the file is written in (type, guid) order, so the index is byte-identical to the sequential scan. `R2TEX_INDEX_THREADS` overrides (1 = sequential).
- Converted-BSP cache. `<gamedir>/r2port/bsp_cache/<map>-<fingerprint>.r2bsp` holds the bspdown output (before the lump-0 entity rewrite and the physics patch, which run on every load) plus the SHA-256 of the R2 source BSP that patch sources match against. The fingerprint is `MapPackageFingerprint` (directory VPK and chunk names, sizes and mtimes, `entity_rewrite::kRewriteVersion`, `kConvertedBspCacheVersion`), so bumping `kConvertedBspCacheVersion` when bspdown output changes is what invalidates it; a hit skips the VPK read, the SHA-256 and bspdown. The source-BSP SHA-256 uses CNG (about 70 ms for 150 MB against 520 ms for `p2p::Sha256`). `R2PORT_BSP_CACHE=0` disables the cache; `R2PORT_LOG_HASHES=1` logs the SHA-256 of the served BSP.

The VPK hook checks the provider's read-mostly name index before issuing its extra native filesystem existence probe, so unrelated misses do not trigger another disk lookup. `R1DELTA_R2PORT_TRACE_MISSES` accepts one or more comma-, semicolon-, or pipe-separated path substrings; it records aggregate counts for all material requests and tracks paths only when they match. `R1DELTA_R2PORT_TRACE_FS` uses the same path-substring filter and records up to 4096 matching filesystem calls in a bounded ring without per-call logging. Values such as `0`, `1`, `false`, `true`, `all`, and `*` do not enable tracing. Run `r2port_dump_stats` to print provider counters and write the captured trace to `<gamedir>/r2port/fs-trace.txt` (the ring holds more entries than the console keeps); normal runs leave both traces disabled. The VPK hook no longer handles `materials/` paths at all; the Open hooks trace as `IFileSystem::Open[...]` and `CBaseFileSystem::Open[...]`.

Diagnostic switch: the environment variable `R1DELTA_R2PORT_NO_MODELS=1` makes the model provider register nothing, so no R2 models are served (maps then show R1's error models where R2 models were needed). It exists for A/B crash triage and is read once at startup.

Foliage cavity bake: R2 alpha-tested foliage (shader sets with `Cav` and `Cut`, vertex-lit variant, no `Vcolt`, no AO map in slot 11: grass, ground plants, bushes, leaf cards; 26 materials over the 20 maps, e.g. `world/glitch/glitch_amber_grass_01`) carries a cavity map in slot 12 (a tuft bake, dark roots and light tips; one texture is shared by the grass materials of different maps). There is no per-vertex or per-instance colour on mp_glitch grass (no VVC, sprp diffuse 255,255,255,255 on all 14,138 blades, constant buffer tint 1,1,1,1); the R2 green lawn is dark grass pushed through the map's colour-correction LUT (`mp_glitch.raw`, which R1 applies identically). `ConvertMaterial` names slot 0 of these materials `r2tex/opamerge/<albedo guid>_<opacity guid or 0>_<cavity guid>`: RGBA8 albedo * cavity^k (k = 0.4, env `R2TEX_FOLIAGE_CAV`, `0` disables the whole foliage path) with the opacity map (if any) merged into alpha, the mip chain rebuilt from mip 0 with premultiplied box filtering and an alpha gain that keeps the share of texels at or above `$alphaTestReference` 0.7 constant (R2 draws the cut-out with alpha-to-coverage, whose coverage is the mean alpha at every mip; R1's alpha test lost blades with each mip: 28 % at mip 0, 9 % at mip 4 on the amber grass). These materials also drop `$envmap`/`$reflectiontint*`/`$envmaptint` (R2 occludes foliage specular with the cavity; R1's cube reflection on up-facing cards is a pale blue sheen). k is a calibration between mp_glitch (grass wants a multiplier of about 0.55) and mp_homestead (about 0.73), see modelanim/GRASS-NOTES.md.

Diagnostic converter variants: the environment variable `R1DELTA_R2PORT_BSPDOWN` is a comma separated list that flips one converter option per token for A/B runs without a rebuild: `csm-rebase` (default on), `csm-no-rebase`, `cubemaps-split` (default on), `cubemaps-single`, `cube-diag=<n>`, `rtl-bake-edge` (default on), `rtl-bake-all`, `rtl-bake-none`, `props-keepfade` (opt-out of rule 23, which raises the fade distance of static props whose origin is far from their geometry so R1's view-to-origin cull keeps water sheets, waterfalls and godrays; BSP cache 23), `empty-shadow-meshes` (rule 17), `no-sun-alpha` (rule 21), `no-rtl` and `no-collapse-envs` (rule 20), `pbr-keep`, `flag2`, `props-keep10`, plus `key=value` tokens `sky-scale=<f>`, `sun-scale=<f>`, `pbr-scale=<f>` (rule 20 sky ambient, sun and PBR light multipliers) and `cube-scale=<f>` (rule 13 cubemap scale); the value must be a finite number >= 0. Unknown tokens and bad values are logged and ignored. Defaults chosen by in-game measurement against R2 frames: rule 20 sky ambient scale `skyAmbientScale` = 0.45 (sun and PBR scales 1.0; the unscaled sky ambient left blue shadows on the ground), and model (VertexLitGeneric) materials get `$envmaptint` 0.25 from r2tex (`R2TEX_MODEL_ENVTINT` overrides, read by the converting process; world materials keep 1). The raw string is part of the converted-BSP cache fingerprint, so variants never share a cache file. Unset gives the defaults of `R2ConverterOptions()`.

Rule 20 light limit (crash found 2026-10-27): the R1 client (`sub_1800FCE60`, run once per map load over the world lights) fills a 256-entry table for every light with flag `0x8` and without `0x10` and then copies it into a static 512 byte array that sits right before the client's ConVar objects. A light with flag `0x8` at GPU slot 255 or higher overruns it and corrupts a ConVar (mp_glitch crashed at signon when a script looked up a persistent-data cvar whose name hash collided with the damaged one). bspdown clears flag `0x8` on every point or spot light at array index 255 or higher, and `check_bspdown.py` verifies it.

Rule 20 real-time light visibility (cone-normalised): R1 lists up to four world-light indices per lightmap texel and has no per-texel weight, while the R2 B plane stores authored spotlight cone times static visibility. A plain byte cutoff therefore dropped the smooth cone tail of spotlights (kodai spot 70 reaches only B 115/155/199 below cone .25/.5/.75). bspdown now reconstructs the native receiver of every weak spotlight texel from the mesh, sort and index lumps (texel centre, or the nearest point of a triangle whose UV footprint touches a sampled border texel; aliased atlas texels keep a slot only when every receiver passes) and keeps the slot when `linear(B) >= linear(187) * analyticCone`. Point lights and B=0 are unchanged (B=0 is always absent), unreachable weak slots are cleared and reported, and reachable but non-invertible UVs are a hard error. The cutoff 187 is a constant: there is no weight option and the earlier plain-threshold path is gone; the only switch is the load-time `no-rtl` token above. The conversion log prints the weak-texel, border, unreachable, alias, disagreement, rescued and rejected counts. Cache effect: `kConvertedBspCacheVersion` must be bumped with this sync. Measurements and fixtures: `lightref\RTL-RESULTS.md` (outside the repo), `check_rtl_visibility.cpp` (12 production fixture cases) and the byte-exact lighting-lump model in `check_bspdown.py`.

`<gamedir>/r2port/patches` may contain `<map>.r2patch` physics patches and `<map>.ain.r2patch` AI-graph packages. Both are keyed to the SHA-256 of the source R2 BSP (`maps/<map>.bsp` exactly as read from the map's directory VPK), which no converter or entity-rewrite change alters, so they survive converter updates. Physics patches replace lump `0x1D` only when that hash matches. An AI-graph package (format version 2, written by `tools/pack-r2port-ain.py pack --map M --ain M.ain --source-bsp M.bsp --out M.ain.r2patch`; the tool refuses anything but a version 37 rBSP) is served as `maps/graphs/<map>.ain` when its header hash matches, its map name matches, its body parses as a v54 graph, at any `developer` level. The provider rebuilds the 12-byte `.ain` header from the live map version and a zero CRC. With `developer` above 0 the retail server (`server.dll` RVA `0x364B80`, the AIN header validation: 1 version < 46, 2 version < 52, 3 map version mismatch, 4 CRC mismatch) compares that CRC with a CRC over the BSP lumps and the info_node, info_hint, traverse and trigger_indoor_area entity text, which a converted map cannot reproduce; the graph is then flagged out of date and the engine builds its own (mp_glitch: 166 nodes instead of 1145). `r2port_ain_hook.cpp` hooks that function (prologue checked, `InstallServerAinCrcGuard` from the `server.dll` load callback) and turns answer 4 into 0 only when the provider has just served a package (`ConsumeServedAinPackage`), so stock maps keep their real check. Verified on mp_glitch: 1145 nodes with `developer` 0 and 1, and with `developer` 0 two grunts walk 2297 u to within 11 and 17 u of the target. With `developer` 1 grunts do not move even on stock mp_box (81 nodes), so that is not caused by the package. Format version 1 packages (keyed to the converted BSP) are ignored and must be repacked. Missing, malformed, or mismatched packages fall back to the converter's physics stub and no AI graph.

When the engine's VPK read path reports a miss before an ordinary filesystem open, the provider writes only that requested BSP or entity file to `<gamedir>/r2port_cache/<map>-<fingerprint>/maps/` and adds the fingerprinted directory as a tail `GAME` search path, after R1 paths. The fingerprint is SHA-256 over the matching R2 directory VPK and chunk-file names, sizes, and modification times, plus `entity_rewrite::kRewriteVersion` and the provider's `kConvertedBspCacheVersion`, so a change to the entity rules or the converter rebuilds the cache. Writing a new fingerprint directory removes the older `<map>-<fingerprint>` directories of the same map. Before materializing, the hook checks the original R1 filesystem so existing R1 files continue to win. The cache stays under `<gamedir>` because the engine mounts it as a `GAME` search path; it contains only generated BSP and entity files (already rewritten as described above) and is removable with `r2port_clear_cache`. Converter and entity-rewrite changes do not affect the `.r2patch` and `.ain.r2patch` packages, which are keyed to the source R2 BSP.

The R1 map-pack material provider (`r1_map_pack_material_provider.cpp`) is registered after the R2 provider for `materials/`. A background thread indexes every `*client_mp_*.bsp.pak000_dir.vpk` in `<cwd>/vpk` (not `client_mp_common`). A request that R1's own lookup missed and the R2 provider could not answer is read from the pack that holds it, for example `materials/cable/zipline.vmt` (R1 forces it for ropes; served from `englishclient_mp_airbase`) and `materials/tools/toolsskybox.vmt`. R1 content always wins, and the first served zipline or skybox file is logged once.

The R2 model provider (`r2_model_provider.cpp`, converter vendored under `engine/r2port/modelconv` by `tools/sync-r2port-modelconv.ps1`) answers `models/**.mdl`, `.vvd`, `.dx11.vtx`, `.vtx`, `.phy` and `.vvc` for the 20 allowlisted maps. R2 models are MDL v53 files with embedded companions inside `englishclient_<map>.bsp.pak000_dir.vpk` and `englishclient_mp_common.bsp.pak000_dir.vpk`; the converter turns them into R1 MDL v52 plus companions. A model whose `.mdl` R1 already has (checked with the native existence probe) is never served from R2, including its companions, because a converted R2 VVC or PHY next to an R1 MDL crashes the client. The converted R1 MDL always has the `@ref` animation and the `ref` sequence as sequence 0 (client-side animating entities (`prop_dynamic`) index sequence 0 unconditionally and crashed in `client.dll+0x104DC` when the converter dropped them), and `ref` carries the pose of the R2 reference animation instead of the bone bind pose (the bind pose draws `escape_pod` on its side and `mobile_hardpoint` collapsed). Every other R2 sequence that plays exactly one animation is converted to R1 animation data (position, rotation and scale tracks, raw and delta records), so `prop_dynamic` `DefaultAnim` names such as the `imc_fan_large_01_animated` `fast_spin` run in game. Sequences that blend several animations (pose parameters), have auto layers, IK rules or locks, animations with local hierarchy, IK rules or the frame-anim layout or with invalid data, and position tracks that need a coarser shared scale than one R1 bone holds are dropped one by one; movement data is discarded; a model whose animation data cannot be converted at all falls back to the one-frame bind-pose output. Conversions are cached per root in `<gamedir>/r2port/cache/models/<revision>/<package signature>/` (bump `kModelCacheRevision` when the converter changes; revision 6 is the first with converted animations). When the BSP is served, a background thread converts every model named in the converted BSP's `sprp` lump and in the five entity files, and registers each model's materials with the material provider as known paths (`PrefetchR2ModelMaterials`); the MDL read registers them again, so a material is known before R1 resolves it. Known paths whose VMT or textures were cached from an earlier map are re-registered after a map change. `r2port_dump_stats` prints the model counters.

Converted models rename every material into the `r2m/` namespace (the converter prefixes each texture directory with `r2m\`, adding one when the MDL has none; `ListModelMaterials` returns the `r2m/` names). The material provider converts `materials/r2m/<R2 material>.vmt` with r2tex like any other material and rewrites a `LightmappedGeneric` shader line to `VertexLitGeneric`. Reason: R2 models reference materials whose R2 shader is a world shader (518 of the 1300 model material references in homestead, eden and colony02). R1 handles those on static props, but on entities (`prop_dynamic`, `script_mover` models such as the homestead water wheels) studiorender draws a mesh with a lightmapped material and materialsystem_dx11 indexes its cubemap SRV table (`unk_180292608`, 32 entries bound to PS slot 9) with an invalid index, crashing in `d3d11!SetShaderResources` (`studiorender+0x1855c` -> `materialsystem_dx11+0x628d4`). It reproduced on mp_homestead within seconds of spawn with only the water wheel models served, and not with `R1DELTA_R2PORT_NO_MODELS=1`. The namespace also keeps the world material of the same name unchanged.

`R2MapPackFileProvider` (in `r2_map_provider.cpp`, registered for `materials/` after the other providers) serves `.vtf`, `.vmt` and `.raw` files that the active R2 map's own directory VPK carries and nothing else answers: the `cloudmask` textures and `color_correction` `.raw` files that only entity keys name (present in all 20 maps' VPKs), plus a few map-specific VMT and VTF files.

## Particles

R2 particle systems are PCF files (`particles/*.pcf`, DMX binary 5 / pcf 2, the same container as R1) inside `englishclient_frontend.bsp.pak000_dir.vpk`. `engine/r2port/particles` (vendored from `C:\Users\r3muxd\tmp\r2port\particles` by `tools/sync-r2port-particles.ps1`) converts the systems the 20 allowlisted maps place with `effect_name` entities, plus everything they reference as children, into one R1 PCF: every system is renamed `r2p_<name>` (so R1's own definitions are never replaced), GUIDs are regenerated, functions R1's client does not implement are dropped (`render_scripts`, `Follow Projectile Arc`, `Sound Meter Scalar`, and `emit_instantaneously by distance`, which becomes a fixed `emit_instantaneously` burst only when the system has no other one), and R2-only attributes are removed. The request list (`r2_particle_requests.inc`, 79 systems; 12 more effect names are identical in R1 and are left alone) and the supported-function list (`pcfconv_tables.inc`) are generated by `tools/gen_tables.py` in the converter directory.

`r2_particle_provider.cpp` serves the result as `particles/r2port.pcf`, built in memory on first use (about 60 ms; no disk cache, so there is no cache revision beyond `entity_rewrite::kRewriteVersion`), and serves R2-only `materials/particle/**` VMT/VTF files from `englishclient_mp_common.bsp.pak000_dir.vpk` (map-specific ones come from `R2MapPackFileProvider`). R1 reads `particles/particles_manifest.txt` once at client Init, and the provider cannot override that file, so `r2port_particles_hook.cpp` detours client.dll `ParseParticleEffects` (RVA 0x1CD5B0, prologue-checked) and, after the original, calls `ReadParticleConfigFile(*(client+0x380F1F0), "particles/r2port.pcf", 0, 0)`. Without an R2 install nothing is served and the call is skipped. `R1DELTA_R2PORT_NO_PARTICLES=1` disables the provider and the `effect_name` rename (read once at startup) for A/B checks. The log line `R1Delta: R2 particles converted ...` reports the conversion; `R1Delta: R2 particle file particles/r2port.pcf loaded=1` the load.

## Entity rewrite

R2 entity text uses classes and keys that R1 does not know. `engine/r2port/entity_rewrite.{h,cpp}` (library with no engine dependencies; CLI and tests in `tools/r2port`, run `tools/r2port/run_entity_rewrite_tests.cmd`) rewrites it:

| Input | Output |
|---|---|
| `prop_dynamic_lightweight` | classname becomes `prop_dynamic`, all keys kept |
| `script_mover_lightweight` | record dropped (R1 `script_mover` does not take its rotator keys) |
| `light_environment_volume` | record dropped (not the same thing as the global `light_environment`) |
| `mp_eden` `info_target` `targetname "spacenode"` | becomes `intro_SpaceNode`, which `mp_eden.nut` looks up |
| `info_spawnpoint_flag` `teamnumber` | key renamed `TeamNum` when `TeamNum` is absent; R1 CTF reads the flag team from it |
| `info_particle_system`, `prop_dynamic`, `prop_dynamic_lightweight` `effect_name` | renamed to the converted `r2p_<name>` system when the effect is one the particle provider converts (see Particles); other effects keep their name and use R1's own definition |

Everything else is preserved byte for byte (line endings included; a test covers CRLF text and checks that the real `light_environment` block is never dropped, reordered or edited; the one edit to a `light_environment` is the cloud/sun state repair below), including `info_target_clientside` (R1's own `mp_mia`/`mp_nest2` use it), `editorclass`/`spawnclass` (never promoted to `classname`), `move_rope` `RopeMaterial "cable/zipline.vmt"` (served by the R1 map-pack material provider), and the keys other providers depend on: `cloudmask`, `cloudoffset`, `color_correction` `filename`. No R2 lightweight network or animation behavior is reproduced. The rewrite is idempotent and fails open: text it cannot parse is served unchanged and logged.

Cloud shadow offset and sun direction (`light_environment` `cloudmask` / `cloudoffset` / `pitch` / `angles`). The R1 server (`CEnvLight::KeyValue`, server `sub_180172FC0`) copies each key into a global the moment it is parsed and never resets between blocks: `cloudmask` into the mask name, `cloudoffset` into the networked `m_cloudOffset` (first three floats) and `m_cloudScale` (fourth float) of the CascadeLight entity (`sub_18010A3D0`), `pitch` into the sun elevation; `CEnvLight::Spawn` (`sub_1801731F0`) takes the sun yaw from the entity's `angles`. The cascade sun direction and the cloud mask offset, scale and projection are therefore the last values seen over all `light_environment` blocks. R2 maps list a dummy skybox `light_environment` (`cloudoffset "0 0 0 0"`, `pitch -51.4284`, `angles 51.4284 122.548 1.30448`, no `cloudmask`) next to the real one. On 16 maps the dummy comes first and the real block wins. `mp_coliseum`, `mp_coliseum_column` and `mp_lf_stacks` have no `cloudmask` in any block. `mp_black_water_canal` lists the real block first and the dummy last, so R1 kept the real mask with offset 0 and scale 0 and the dummy sun direction: the world pixel shader's cloud mask term (`cb2[26..27]`, projection of the world position into the mask) was evaluated with that degenerate projection (vertical streaks on rock walls, a tiny repeating pattern on prop panels, both gone with `mat_cloudmask 0`), and with the offset repaired alone the cloud shadow was projected along the wrong sun direction (rock in blue cloud shadow where R2 shows warm light). The rewrite finds the last `light_environment` with a `cloudmask` and gives every later `light_environment` that sets `cloudoffset`, `pitch` or `angles` itself the real block's value for those keys; nothing else in the block, the block order and every other map's text are byte-identical (checked over the 20 R2 env partitions: only `mp_black_water_canal` changes). Not applied to `mp_coliseum` / `mp_coliseum_column`: their real block has a 22 degree sun and no cloud mask, and the real direction there (set at run time with `light_environment` keyvalues, no file change) darkens the whole arena floor with `csm_enabled 1`; the reverted attempt in `bdbc345` moved the dummy first with the same result. The cause is not established (the floor is bright with `csm_enabled 0`, so the cascade shadow term darkens it), and it stays open.

One non-idempotent step runs on lump 0 only, after the rewrite: `RaiseFlagSpawnOrigins` lifts every `info_spawnpoint_flag` origin by `kFlagSpawnLift` (8 units). R2 authors the flags on the floor; the R1 server drops a flag spawnpoint to the floor itself but removes one whose origin starts inside solid, and the converted collision can put the floor a unit above the R2 origin. `mp_lf_stacks` lost its second flag that way (z 0.0006 against a floor at 1.03); with the lift both flags exist in CTF and the spawnpoints settle on the floor as before. `mp_glitch` is unchanged (both flags still end at z 2.03).

The provider applies it in two places: to each of the five partition files (`_env`, `_fx`, `_script`, `_snd`, `_spawn`) as they are read from the R2 package (`Size` and `Read` both report the rewritten bytes; the result is cached per map), and to lump 0 of the converted BSP, where the CTF flag spawnpoints live (the BSP is repacked with the same lump replacement the physics patch uses, so game-lump offsets stay valid, and it is left untouched when no rule matches). Each rewrite that changes a file logs one line, `R1Delta: R2 entity rewrite map=<map> <file|bsp-lump=0> entities=<in>-><out> ...`. Bump `entity_rewrite::kRewriteVersion` whenever the output for the same input changes.

## Titanfall 2 install search

The player's own Titanfall 2 install (its `vpk` and `r2/paks/Win64` rpaks) is found by one search order, implemented twice and kept identical: `TitanfallLocator.FindTitanfall2` in `launcher_ex/TitanfallFinder.cs` and `DiscoverR2Install` in `engine/filesystem/r2_map_provider.cpp`. Change both together.

1. Explicit path. The launcher's `manualPath` argument (a root directory, or a file directly inside it; the launcher has no saved setting yet) and the `R1DELTA_TITANFALL2_PATH` environment variable (the engine has only this one). An explicit choice that does not validate ends the search with no result; it never falls back to another install.
2. `HKLM\SOFTWARE\Respawn\Titanfall2` value `Install Dir`, 64-bit then 32-bit registry view.
3. Uninstall entries under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` (both views) whose key is the EA product GUID `{4BD80373-FEE7-45B6-8249-6E8E98717405}` or `Steam App 1237970`, or whose display name reads Titanfall 2 (`^Titanfall\S{0,3}\s*2\b`, case-insensitive; the EA installer writes a mangled trademark sign): the `InstallLocation` value.
4. Steam. Roots from `HKLM\SOFTWARE\Valve\Steam`, `HKLM\SOFTWARE\WOW6432Node\Valve\Steam` and `HKCU\Software\Valve\Steam` (values `InstallPath`, `SteamPath`), then every library in each root's `steamapps\libraryfolders.vdf` (both the `"path"` and the older numeric-key layouts). In each library: the `installdir` from `appmanifest_1237970.acf`, then `steamapps\common\Titanfall2`, then `steamapps\common\Titanfall 2`.
5. `Titanfall2` and `Titanfall 2` under `\`, `Games`, `Games\EA`, `EA Games`, `Program Files\EA Games`, `Program Files (x86)\Origin Games`, `Program Files (x86)\Steam\steamapps\common` and `SteamLibrary\steamapps\common` on every fixed or removable drive.

Every candidate, whatever its source, must pass the same validator: `bin\x64_retail\rtech_game.dll`, at least one `.rpak` in `r2\paks\Win64`, a `*client_mp_common.bsp.pak000_dir.vpk` and `client_mp_common.bsp.pak000_000.vpk` in `vpk`, and no `r1\gameinfo.txt` (that marks Titanfall or R1Delta, so the Titanfall finder and this one can never accept the same folder). The engine runs the search once, on first use, and logs `R1Delta: R2 map provider install discovery found <path> via <source>` (or that it found none, or that the environment variable is set but not a valid install).

## Shader track

`engine/r2port/shaders` compiles our own HLSL at runtime and lets a converted VMT use it by name. R1's `screenspace_general` material class names its shaders through `$pixshader "<name>"` (file `shaders\fxc\<name>_ps40.vcs`) and `$vertexshader "<name>"` (`<name>_vs40.vcs`). `r2_shader_compiler.cpp` runs `D3DCompile` (`ps_4_0` / `vs_4_0`) and wraps the DXBC as a VCS v6 file with the same layout as the stock files; `r2_shader_cache.cpp` keeps the files under `<gamedir>/r2port/shadercache` (rebuilt when the source hash or `kCacheRevision` changes) and `R1BaseFileSystem_Open` (factory.cpp) opens them by absolute path when R1's own file system misses a `shaders\fxc\...` request. They are real files, not provider memory handles, because the shader loader calls `AllocOptimalReadBuffer` on the handle, which the provider memory handles do not implement. Sources are embedded in `r2_shader_sources.h`; `<gamedir>/r2port/shaders/<name>.hlsl` adds or overrides one without a rebuild. A source that fails to compile or link logs `R1Delta: R2 SHADER BUILD FAILED` with the compiler text and writes no file (the material then does not draw); `r2port_shaders` lists the state and `r2port_shaders_rebuild` recompiles. Offline check: `.build\build-r2-shader-cli.cmd`, then `.build\r2_shader_cli.exe <outdir>`.

Contract learned from the stock default vertex shader `screenspaceeffect_vs40` and from game runs: b0 = the 20 floats `$c0_x..$c4_w`; b2 `CBufCommonPerCamera` and b3 `CBufModelInstance` are bound for the vertex shader; t0..t3/s0..s3 = `$basetexture`, `$texture1..3`; a custom `$vertexshader` is always asked for static combo 0 (the engine only varies the combo for the default VS), so the vertex file is the transformed build and `$vertexshader "<name>_vcol"` selects the vertex-colour build. Verified in game on world brushes (`mp_coliseum`): custom pixel shader with the default vertex shader, and custom vertex plus pixel shader reading b2/b3, UVs, a 2D texture and the view direction. Not working yet: the same materials on the coliseum dome static prop draw nothing. See `r2port/shaderlab/SHADER-TRACK.md`.

Pixel-shader override (`r2_shader_override.cpp`): R1's `UnlitTwoTexture` class fills its draw state (`a4+24` pixel shader name, `a4+72` pixel combo) in the vtable-slot-9 function at materialsystem_dx11 RVA 0x2FA10 (checked against the retail build stamp and prologue). The hook calls the original and, for a material whose `$godrayMinFadeDist` is `7700 + id` (a parameter the class ignores while `$godray` is 0), swaps in our pixel shader from the cache. Props and brushes keep the stock vertex shader, vertex format and draw path, which `screenspace_general` does not do on static props (adding a compressed-normal NORMAL input to the custom vertex shader did not help; cause still unknown). Id 1 is `r2_ut_dome`, a copy of the stock static combo 0x110 (fresnel + `$addlayers`, no fog, dyn 0; disassembled from `unlittwotexture_ps40.vcs`) whose layer 2 is a `TextureCube` at t1 sampled along `TEXCOORD7`; the material must set `$nofog 1` because our file has one dynamic variant. r2tex emits it for `world/test/kodai_fake_screen_01_world`, `skies/boomtowncubemap_grave` and `skies/boomtowncubemap_desert` (default on; `R2TEX_SHADERS=0` restores the scan-line-only VMT). Verified in game on `mp_coliseum` (static prop dome) and `mp_grave`.

LightmappedGeneric override (world brushes, `r2_shader_override.cpp`, `r2_shader_source_lmg.h`, env `R2_LMG_PBR`, default OFF: with the variable unset there is no hook and no LMG shader is compiled). Hook on the class' vtable slot 9 (RVA 0x28610, prologue checked), same idea as above: after the original fills `a4`, an eligible draw gets our pixel file (`r2_lmg_pbr_ps40`) and static combo = index * 12; the stock vertex shader, vertex format and draw path stay. Values: `1` = materials with `$treesway 7701`, `all` = every eligible material, `neutral` / `mark` = validation shaders (stock formulas only / same tinted), `dbg6|7|8` = panel visualisations, `log` or `+log` = write every distinct draw state and reject reason to `<gamedir>/r2port/lmg_log.txt`. Eligible = stock `lightmappedgeneric_ps50` + `_vs40`, real-time-light path on (render flags dword at RVA 0x38FB2C: `& 0x1400000 == 0x400000`, `& 0x2000000 == 0`), a vertex combo with tangents (`(a4+76)/2 % 6` is 2 or 5), `$basetexture`, `$bumpmap`, `$reflectionTint`, no `$vertexcolor`, no godray; single layer, or two layers with `$baseTexture2`, `$bumpmap2`, `$reflectionTint2`, `$blendModulateTexture`. The pixel file holds 5 static combos x 12 dynamic combos (lights / shadow mode / fog flavour exactly like the stock file) because R1 links the vertex and pixel stage by REGISTER: a pixel shader must declare the same register layout as the vertex combo (TEXCOORD1.xy occupies a register when a detail texture is present; TEXCOORD3 is a float4 for two layers). Stock terms were reconstructed from the reflected stock bytecode (lightmap decode, bumped sky weight, CSM PCF with cloud mask, real-time light list from t20, hardware lights, two fog flavours, `c_lightScale`); `neutral` reproduces the stock frame (median pixel difference 0, mean 0.1 to 1 of 255 on three maps, remaining difference is the scene itself). Added R2 terms: GGX-shaped specular driven by gloss, F0 from `$reflectionTint` (re-encoded to the stored value, see PHASE2.md), AO on lightmap, sky and ambient, cavity on specular, and a highlight from the baked light direction (lightmap plane B). Material data reaches the shader packed: single layer `$detailColor` (t4, `$detailColorMode 1`) = r gloss, g AO, b cavity; two layers `$blendModulateTexture` b = gloss layer 1, a = gloss layer 2 plus `$treesway 7701`. r2tex does not emit these yet.

Credit: ficool2's sdk_screenspace_shaders documented the screenspace_general register convention (used with the author's permission); a shader author who provided hints on the Uber material model. No code from either is included.

## Ambient occlusion

`engine/r2port/ao` (`r2_ao.cpp`, `dxbc_patch.cpp`). Everything is default OFF: with every `r2port_ao_*` / `r2port_sso` variable at 0 no hook is installed and nothing runs per frame. The variables are archived (they persist in the config), live, and a hook is only installed when one of them is first set nonzero. Unsupported builds (materialsystem_dx11 timestamp/size, HBAO+ wrapper prologue, `GFSDK_SSAO.win64.dll` timestamp 0x537DE692 and vtable slot) install nothing and log one warning.

What R1 does: NVIDIA HBAO+ 2.1.2 (`GFSDK_SSAO.win64.dll`, "r2_1") is called once per frame from materialsystem_dx11 RVA 0x17800 (after the opaque pass), and multiplies the AO into the scene colour target. Stock cvars: `r_hbaoEnabled` (default 0), `r_hbaoRadius` 1.0 (metres), `r_hbaoIntensity` 1.0, `r_hbaoExponent` 4.0, `r_hbaoBias` 0.1, `r_hbaoBlurRadius` 8 (only 4 or 8), `r_hbaoBlurSharpness` 4.0, `r_hbaoDepthMax` 2000. We swap vtable slot 2 (RenderAO) of the GFSDK renderer (decoded: `RenderAO(self, ctx, input, params, rtv, mask)`; input +8 projection, +20 metersToViewUnits, +24 depth SRV, +32 viewport; params dword 2 = DetailAO, 9 = blur radius enum 0/1/2 = 2/4/8 px).

Variables (console, `r2port_ao_status` prints the state):

| variable | default | effect |
|---|---|---|
| `r2port_ao_timing` | 0 | 1 = GPU timestamp queries around the HBAO+ call (and the composite), average/min/max logged to the console every 240 frames |
| `r2port_ao_blur` | 0 | 2 / 4 / 8 = force the blur radius in pixels (2 px is not reachable through `r_hbaoBlurRadius`) |
| `r2port_ao_detail` | 0 | HBAO+ DetailAO 0.2 to 1 (finer contact shadows; R1 always passes 0) |
| `r2port_ao_luma` | 0 | 0..1: AO fades out on bright pixels: `scene * lerp(ao, 1, saturate((luma - lo) / (hi - lo)) * k)`; draws one full-screen pass (scene copy + composite) |
| `r2port_ao_luma_lo` / `_hi` | 0.03 / 0.35 | linear scene luma where the fade starts / ends (display value about 90 / 165) |
| `r2port_ao_dump` (command) | | writes the next frame's HBAO+ depth input to `<gamedir>/r2port/depth_dump.r2d` (u32 'R2D1', w, h, format 0 = float depth, float projection[16], float metersToViewUnits, depth floats) for the offline benchmark |

Cost, measured in game (RTX 5080, 3440x1440 windowed, `R1DELTA_BACKGROUND_FPS=0` uncapped, `mat_vsync 0`, `fps_max 0`, `mat_force_tonemap_scale 1`, fixed camera, 3 runs of 6 s per cell; `maps/ao/*.json`, `maps/ao/BENCH-RESULTS.md`): GPU time of the HBAO+ pass 0.31 to 0.41 ms (min / average; 0.40 average in the first session, 0.37 in the last), blur 4 the same, blur 2 0.33 to 0.35, no blur 0.30 (the blur is only 20 %), radius 0.5 / 2.0 no change, DetailAO 0.5 0.42. R1 hardcodes step count, depth storage and resolution: a sweep of every parameter dword of the 2.1.2 struct (standalone benchmark) finds no cheaper mode in the DLL (dwords 15 and up are ignored). CPU side (render thread, `r2port_ao_timing 2`, QueryPerformanceCounter, no GPU queries): the whole R1 HBAO+ function including its D3D state save/restore takes 0.022 ms average (max 0.09 ms) and the GFSDK call itself 0.015 ms: there is no CPU stall, sync or per-frame allocation to find; the cost is GPU time. Whole frame: at about 600 fps (a CPU bound scene) `r_hbaoEnabled 0` versus 1 was 692 versus 574 fps (median of 3 runs; 1.45 ms versus 1.74 ms, i.e. +0.30 ms) and earlier 570 versus 544 (kodai) and 513 versus 490 (glitch). The cost is constant per frame and scales with pixels: standalone (same DLL, same arguments, synthetic depth) 0.073 ms at 1280x720, 0.156 at 1920x1080, 0.276 at 2560x1440, 0.384 at 3440x1440 = 0.075 ms per megapixel on an RTX 5080 (about 56 TFLOPS). Estimate for a GPU k times slower at the same resolution [INFERENCE, not measured, there is no slower GPU on the test machine]: added ms = 0.075 x megapixels x k, e.g. 1080p on a GPU 8x slower about 1.2 ms (7 % of a 16.7 ms frame, 17 % of a 6.9 ms frame), 16x slower about 2.5 ms (15 % / 36 %), 1440p 16x slower about 4.4 ms (26 % / 64 %). So 0.4 ms is small on a 5080 but a large share of the frame on weak GPUs, which is why the cheaper backend below exists. FXAA (`mat_fxaa_enable 1`) and `r_txaaEnabled 1` did not change the HBAO+ pass time (0.40 to 0.42 ms; whether `r_txaaEnabled` actually engaged TXAA in that run was not verified). To measure on another machine: `mat_vsync 0`, `fps_max 0`, fixed spot, `r_hbaoEnabled 0` then 1, 3 runs each, plus `r2port_ao_timing 2` for the CPU side and `r2port_ao_timing 1` for the GPU milliseconds (GPU timestamp queries: a user reported a driver crash with timestamp queries in an earlier idea; use mode 2 first).

Note: setting `r_hbaoRadius`, `r_hbaoIntensity`, `r_hbaoExponent` from the console did not change the values read by the HBAO+ call in our tests (the cvars kept 1.0 / 1.0 / 4.0), so `r2port_ao_radius`, `r2port_ao_intensity` and `r2port_ao_exponent` override them in the hook. The same variables feed the XeGTAO backend.

AO quality tiers (`r2port_ao_tech`, default 0, needs `r_hbaoEnabled 1`; every tier falls back to HBAO+ on a failure and logs why):

| `r2port_ao_tech` | backend | GPU ms at 3440x1440 in game (min / avg) | at 1080p (standalone) | % of a 16.7 ms / 6.9 ms frame at 3440x1440 (avg) |
|---|---|---|---|---|
| off (`r_hbaoEnabled 0`) | none | 0 | 0 | 0 / 0 |
| 0 (stock) | NVIDIA HBAO+ | 0.31 / 0.37 | 0.156 | 2.2 % / 5.4 % |
| 1 | XeGTAO High, full resolution, 2 denoise passes | 0.40 / 0.51 | 0.17 | 3.1 % / 7.4 % |
| 2 | XeGTAO High, half resolution, 2 denoise passes | 0.16 / 0.20 | 0.07 | 1.2 % / 2.9 % |
| 3 | XeGTAO Medium, half resolution, 1 denoise pass | 0.12 / 0.16 | 0.056 | 0.96 % / 2.3 % |

Recommended for weak GPUs: tier 2 (best non-temporal look, about 2.4 to 2.6 times cheaper than HBAO+), tier 3 on very weak GPUs; on a GPU k times slower multiply the ms by k. The XeGTAO backend is a compute-shader port of Intel's XeGTAO (MIT) in `r2_xegtao.cpp`: it reads the same depth SRV and projection HBAO+ gets, writes the same R16 AO texture and then follows the HBAO+ composite path (`r2port_ao_luma`, `r2port_sso`). Look: R1 has no TAA, so XeGTAO's noise pattern is fixed: grainier than HBAO+ and more occlusion on large concave surfaces, and at half resolution a thin dark rim behind thin occluders. Use `r2port_ao_intensity 0.7` to sit near the HBAO+ darkness in interiors (kodai props: mean luminance ratio versus AO off 0.84 versus HBAO+ 0.89 at intensity 1.0; open scenes 0.97 versus 0.99). It fades to 1.0 with view depth (1200 to 2000 units, like HBAO+'s `r_hbaoDepthMax`) and treats the sky as unoccluded. Bugs found on the way: the compute shaders read zero depth while the scene depth was still bound as the depth-stencil view (fixed by unbinding the output merger first), and the engine's depth matrix has an infinite far plane (row-vector, `m[10] = -1`, `m[14] = -7`), which XeGTAO's linearisation handles. Look tests are limited: validated on two real depth dumps (`maps/ao/`, kodai overlook and interior) and compared in game on kodai and glitch only; on glitch p7 / p6 tier 2 is -1 % / -8 % mean luminance relative to the stock HBAO+ frame (`maps/ao/tier_frames`).

Presets (`r_hbaoEnabled 1`; frames under `maps/ao/tier_frames`; on glitch the camera was not frozen between presets, so differences are relative to the `stock` frame, not to AO off): `stock` = R1 defaults; `crisp` = `r2port_ao_radius 0.6`, `r2port_ao_intensity 1.3`, `r2port_ao_exponent 3`, `r2port_ao_blur 4`, `r2port_ao_detail 0.4` (about 0.42 ms, +3 / +5 % luminance versus stock: tighter, slightly lighter); `wide` = radius 2, exponent 2, intensity 1.2 (about 0.40 ms, +4 %); `tier B` = `r2port_ao_tech 2` with `r2port_ao_intensity 0.7`; `tier C` = `r2port_ao_tech 3` with intensity 0.7; add `r2port_ao_luma 0.9` to any of them to fade the AO out on sunlit pixels (measured on glitch: AO stays 0.85 in the darks and is 1.00 above display value 170). None of them reproduces R2's contact darkening, which comes largely from R2's baked AO textures (channel study in `shaderlab/CHANNELS.md`).

Specular occlusion (SSSO, `r2port_sso`, `r2port_sso_strength`, env `R2_SSO`; default off): `dxbc_patch.cpp` rewrites the stock model and world pixel shaders when they are created. Findings (`maps/ao/SSSO-PATCH-RESULTS.md`): `vertex_and_unlit_generic_ps50.vcs` (models: viewmodel, props) and `lightmappedgeneric_ps50.vcs` (world) have 70,624 env-bearing stored shader records, each with exactly one `sample_l` of the cube at t5/s5; t31 is free in every original record and 37,792 already read `SV_Position`. The patch adds an `ld` of an occlusion texture at t31 (indexed with `SV_Position.xy`, adding the input and its signature when missing) and multiplies the cube sample RGB by `1 - occ`; an unbound t31 reads 0, i.e. no change. All 70,624 patched records pass D3DDisassemble, D3DReflect, the DXBC checksum and `CreatePixelShader` on the RTX 5080 and on WARP, and a hardware render of three stock combos matches the reference within FP16 rounding (occlusion 1.0 = black cube exactly, 0.25 within 5e-4). In the engine the AO pass writes `occ = (1 - ao) * r2port_sso_strength` into one of two R8 textures and binds it at t31 after the HBAO+ call, so the factor is the PREVIOUS frame's AO (one frame of lag; the engine leaves t31 alone: `r2port_ao_status` counts it still bound at the start of every next frame, lost 0). It is the fixed approximation `so = 1 - strength * (1 - ao)`, not the Lagarde roughness-dependent formula (no stable roughness register across the compiled variants). Shaders are patched as they are created, so use env `R2_SSO=1` (patching from the first load; the cvar alone can come too late for shaders created at start-up); patching every env shader would cost about 17 s of CPU, in practice only the shaders of the loaded map are created (about 650 patched records on kodai). Test aids: env `R2_SSO=zero` multiplies every patched env term by 0 (the viewmodel scope reflection disappears: proof that the patched shaders are the ones drawn), `r2port_sso_debug 1` forces full occlusion, `r2port_sso_probe` logs min/mean/max of the occlusion and AO textures. Result in game (kodai interior, strength 1, crisp AO): the env term is reduced only in recesses and edges (3.5 % of pixels darker by more than 4 display units, 0.1 % brighter, mean -0.5; `maps/ao/sso_props_final.jpg`); on open surfaces AO is about 1 so nothing changes. Limits: one frame of lag (a moving camera shows trailing occlusion on reflective surfaces); render targets of other sizes (cube captures, camera screens) read the wrong texels; the effect is subtle by construction. The gun showed a magenta env term in some test builds (the model's cube map): it is the same with and without the patch, not this feature.

Credit: NVIDIA HBAO+ is called as R1 does; the XeGTAO backend is Intel's XeGTAO (MIT, https://github.com/GameTechDev/XeGTAO) ported to D3D11 compute with half-resolution passes of our own (licence text in `r2_xegtao.h`); the DXBC checksum follows AMD GPUOpen's public `DXBCChecksum.cpp`; the specular occlusion idea is from the Frostbite PBR notes (Lagarde and de Rousiers, 2014); a shader author's notes on the Apex AO/SSSO stack were used as a checklist (facts only, no code, nothing of his files is in the repository).

## Post effects

`engine/r2port/postfx` adds two opt-in screen effects that stock R1 does not have, both OFF by default (all cvars 0 = stock look, bit for bit, and no hook is installed). They share one full-screen pass that runs right after the client's final `engine_post` draw and before the HUD.

| cvar | default | meaning |
|---|---|---|
| `r2port_display_curve` | 0 | R2-style display curve strength, 0 (off) to 1 |
| `r2port_sharpen_amount` | 0 | RCAS sharpening strength, 0 (off) to 1 |
| `r2port_sharpen_denoise` | 0.5 | RCAS noise attenuation, 0 to 1 (0.5 = AMD's FSR_RCAS_DENOISE) |
| `r2port_sharpen_width` | 1 | RCAS tap distance in pixels, 1 to 4 |
| `r2port_postfx_stats` | 0 | 1 = log the average frame time every 300 frames (console and `<gamedir>/r2port/postfx_stats.txt`); installs the hook so frames can be counted |
| `r2port_postfx_srgb` | 1 | diagnostic: 1 = the pass converts between the sRGB views and display values (correct); 0 = treat sampled values as display values |

`r2port_postfx_status` prints the build check, hook state, pass and skip counters and the material state. The first four cvars are `FCVAR_ARCHIVE_PLAYERPROFILE` like the other `delta_` cvars, so a value set in the console is saved in `profile.cfg`; the same lines work in `cfg/autoexec_delta.cfg`:

```
r2port_display_curve 0.5
r2port_sharpen_amount 0.5
```

**Seam** (client.dll, retail R1 build stamp `0x55038DB8` / size `0x39A4000`, checked at run time together with the prologue bytes of the hook target and of the `_rt_FullFrameFB` accessor; any mismatch logs one warning and the cvars do nothing). `sub_1802AA380` (RVA 0x2AA380) is the client's post pass: copies the frame into `_rt_FullFrameFB`, runs the bloom chain, draws `dev/engine_post` through `IMatRenderContext::DrawScreenSpaceRectangle` (vtable +936) with destination `0,0,w,h` and returns 1 when it drew. Under `mat_queue_mode` the first call only queues itself and returns 0; the queued call on the render thread does the work and goes through the same detour. After the original returns 1 the detour copies the target into `_rt_FullFrameFB` (`CopyRenderTargetToTexture`, vtable +976, which `engine_post` has just consumed) and draws the material `r1d/post` (`screenspace_general`, runtime shader `r1d_post`, VMT served from memory by a provider) over the same rectangle. Only engine interfaces are used, so the engine's state tracking stays consistent.

The open questions from the study, answered in game:
- Target format: the bound render target is `R8G8B8A8_UNORM_SRGB` (texture `R8G8B8A8_TYPELESS`, 1280x720 in the test), and the sampled copy decodes sRGB too. With the shader treating the values as display values the output equalled `enc(curve(dec(a)))`, so the shader converts (`c0.w = 1`, default of `r2port_postfx_srgb`); with that the identity case round-trips within 8-bit rounding (offline on WARP, curve 0 and sharpen 0 is bit exact).
- Rectangle: the engine draws `0,0,w,h` with `w,h` from the view struct; the pass uses the same. It is skipped (one warning, stock path) when the view does not start at 0,0 (split screen; not testable in the MP client, so only the guard exists), when the engine_post destination is halved (the client convar that `sub_1802AA380` tests at `+92`), or when the render target is not the size of `_rt_FullFrameFB`.
- HUD ordering: with `cl_drawhud 1` and curve 1 only 0.1 % of the HUD pixels equal the curved HUD-less frame, i.e. the HUD is drawn after the pass and is neither curved nor sharpened (`maps/postfx/hud` frames).
- `FindMaterial` and the first `FindVar` must run on the main thread: `Bind()` on the render thread finishes a new material through a call into the main thread, which deadlocks against the main thread waiting for the render thread (seen as a hung client, stacks in `maps/postfx`). The detour prepares and finishes the material on the main thread (the client loads on it) before any render-thread draw.

Failure behaviour: a fault inside the pass (SEH guard) switches the effects off for the rest of the session with one warning; a missing shader (`r1d_post` is an embedded entry of the shader cache, see `r2port_shaders`) or a material that does not load disables them with one warning. With both effect cvars at 0 and `r2port_postfx_stats` 0 no hook exists (the hook is created on the first nonzero cvar and disabled again when all return to 0).

**Display curve.** `tools/r2port/make_display_curve.py` inverts R1's measured response (about L^0.57, `maps/flat/responses.json`) and applies R2's (near linear toe, filmic shoulder) with PCHIP interpolation between the exposure-ladder knots, shifted by the exposure offset `SHIFT` = 0.15 (picked by scanning 0 to 0.4 against the FlatLook auto-exposure frame pairs: 0.15 gives sd/p10/p90 ratios closest to 1 over the three maps, 0.085 from the pixel-pair fit left kodai too dark), linear below display value 16 where the ladder has no data. It writes the 65-entry table into `r2_shader_source_postfx.h`; `lerp(identity, curve, strength)` is applied per channel on display values before sharpening. Measured display mapping R1 to R2 (values 0..255): 16>6, 32>19, 48>37, 64>59, 80>84, 96>110, 128>154, 160>186, 192>211, 224>234.

Validation in game (kodai, glitch, complex3, mp_lf_township, mp_lf_stacks; the R1 pose is the R2 reference pose, auto exposure, HUD and viewmodel off, `r_hbaoEnabled 1`, same config as FlatLook; geometric mean over spots of R1/R2, 1.0 = R2; `maps/postfx`):

The curve fixes what it was fitted for: the contrast statistics (sd, p10, p90) move toward R2 on every map at both strengths (strength 1 overshoots sd slightly on glitch and complex3, and takes kodai p10 .88 and glitch .80 below R2). It does not fix lighting differences: the per-pixel luminance error against R2 is unchanged to slightly worse (mean absolute difference 30.1 > 31.1 kodai, 24.2 > 23.4 glitch, 47.5 > 48.1 complex3, 31.7 > 32.1 township, 27.3 > 28.0 stacks at strength 1), and at strength 1 the per-spot mean ratio moves more than 5 points away from R2 at 11 of 40 spots (strength 0.5: kodai u_shadow, township s0), e.g. kodai far .80 > .72 and complex3 s5 2.54 > 2.62 (that interior is a lighting mismatch, not a transfer one). A single curve cannot be exact per map, which is why the strength is tunable and the default is 0; 0.5 is the suggested first try.

**RCAS.** `r1d_post` also contains the RCAS pass from AMD FidelityFX FSR 1 (`ffx_fsr1.h` v1.20210629, MIT): 5-tap cross, luma-proxy noise detector, per-channel clip-free lobe limited to 0.25 - 1/16, no reciprocal approximation (exact `rcp`), one `1e-7` epsilon on two reciprocals. It reads the curved neighbours, so sharpening follows the curve. Offline against a CPU transcription on D3D11 WARP the compiled VCS matches to <= 4e-6 for ten curve/sharpen/denoise/width/encoding combinations. In game on kodai (3 spots) the mean Laplacian magnitude of the frame rose to 1.26 to 1.31x at amount 0.5, 1.85 to 1.99x at 1, 2.6 to 2.9x at 1 with denoise 0, 1.66 to 1.75x at 1 with width 2; the share of near-black pixels (all channels <= 1) rises by up to 0.3 points at amount 1 (kodai far 1.49 % > 1.78 %; 2.28 % at denoise 0) and clipped-white share is unchanged; crops in `maps/postfx/rcas`. Credit: AMD FidelityFX FSR1 (MIT); a shader author provided hints on the TF2/Apex sharpening stage and its placement. No code or bytecode of his private files is in the repository.

**Cost** (kodai u_decal, 1280x720, `R1DELTA_BACKGROUND_FPS=0` uncapped, paused scene, `r2port_postfx_stats 1` in every case, i.e. the hook is installed even for "off", 3 interleaved rounds, 4 to 6 windows of 300 frames each): median frame time 2.88 ms (347 fps) off, 3.02 ms (331 fps) curve 1, 3.03 ms (330 fps) sharpen 1, 2.99 ms (335 fps) both: about 0.1 to 0.15 ms per frame (3 to 5 %), run-to-run spread 2.75 to 3.15 ms. GPU timestamp queries were removed: issued from the pass they made the NVIDIA driver fault on its own worker thread (`nvwgf2umx`, read of 0x18, twice within seconds); without them nothing faulted. The "off" figure includes the hook, so the stock cost is at most that.

Regenerate the shader after changing the curve: `python tools/r2port/make_display_curve.py [--shift S] [--print]` (needs numpy and scipy), then rebuild; a loose `<gamedir>/r2port/shaders/r1d_post.hlsl` overrides the embedded source without a rebuild.

## Known gaps

- The cubemap scale is the upper bound of a per-cubemap scale `clamp(cma_gain * CMA, 0.25, 4.0)` (rule 13b, CMA = the per-cubemap multiplier array stored in R2's `cubemaps.hdr.vtf`; `mp_forwardbase_kodai` CMA 5.0 3.26 2.34 8.89 0.88 0.86, `mp_glitch` 1.3, `mp_lf_stacks` 0.7), and rule 13c adds up to 96 copied cubemap samples so R1's nearest-sample lookup picks the cube R2 assigned to the light probe refs (lump 0x68 trailing int32, a working hypothesis). On kodai this halves the share of white (> 235) pixels on the R1 B3 Wingman viewmodel (startB 8.6 % -> 2.7 %, cap2 7.9 % -> 2.4 %, u_decal 5.0 % -> 2.4 % in a 160 x 340 px box), but an R2/R1 gun comparison is impossible (different viewmodel meshes and materials), the indoor `h02` view got brighter (3.1 % -> 7.1 %), and an extra cap of 2 (`cube-scale=2`) did not measurably change the gun in a same-weapon A/B. The global default of 4.0 was measured on `mp_wargames` only. On `mp_glitch`, a fixed-view screenshot (client at 2560 468 264, angles 12 45 0, exposure locked) came out the same with scale 1/6 and with 4 (mean absolute difference 0.025 of 255); that view apparently does not sample the cubemaps.
- `mp_forwardbase_kodai` still looks flatter than R2 after the material fixes (decal z-fight, scanner screens, cloud sheets). Measured over the same 1200 x 600 window with the gun and minimap masked, R1 vs R2 luminance standard deviation is 36.8 vs 53.5 at u_decal (0.69), 30.2 vs 48.6 at u_dust (0.62), 32.1 vs 50.3 at u_shadow (0.64); p10 is 1.5 to 2.5 times R2's and p90 is 0.64 to 0.80 of R2's (before the cloud fix u_dust was 26.9 / 61.8 / 134.8). A sun-scale / sky-scale grid (`mat_sun_scale` 1 to 2, `mat_sky_scale` 0.7 to 1.6, same effect as the rule 20e options) did not fix this: it helps the sunlit kodai spots at sun 1.5 to 2 but over-brightens `mp_thaw` (mean luminance +10 to +20 %), and interior and shadowed views do not react to it. The remaining gap is the R1 display transfer of lightmapped surfaces (see `maps/interior/RESULTS.md`).
- The entity rewrite changes only class names, a few keys and two dropped records. `editorclass` roles, `info_hardpoint` assault targets (the static audit expects CP/Uplink asserts on `mp_glitch`, `mp_lf_deck` and `mp_lf_stacks`; not run), the `gamemode_at` versus R1 `gamemode_atdm` spawn tag, and R1's disabled FFA spawn filter are not handled; they need R1 script or BSP-aware changes. R2 trigger volumes are handled by the trigger brush bake below. Classes R1 does not register (`envmap_volume`, `func_wallrun_curve`; the rewrite also drops `script_mover_lightweight` and `light_environment_volume`) are listed in one log line per map load ("R2 entity classes R1 does not register"); the full census is `C:\Users\r3muxd\tmp\r2port\entityport\CENSUS.md`.
- Trigger brush bake (`engine/r2port/trigger_brush.{h,cpp}`, called from `RewriteConvertedBspEntities` in `r2_map_provider.cpp`): R2 keeps trigger brushes in the entity text (`*trigger_brush_<b>_plane_<p>`, `*trigger_bounds_*`) and gives triggers no `model`, so a converted map spawned every `trigger_hurt`, `trigger_out_of_bounds`, `trigger_soundscape`, `trigger_indoor_area`, `trigger_capture_point` and `trigger_multiple/once` without a volume (1,202 entities over the 20 maps; 435 of them `trigger_out_of_bounds`, which sit in BSP lump 0). The bake appends one R1 brush model per trigger entity to the converted BSP (lumps 0x0E, 0x56, 0x57/0x58, 0x5C, 0x01, 0x5D, 0x5E, same layout as stock R1 trigger volumes: single-primitive geosets, contents 0x1, TOOLS\TOOLSTRIGGER side textures) and rewrites the entity text (`"model" "*N"`, plane/bounds keys removed) in lump 0 and the five `.ent` files, which the provider serves from the map state. Verified in game on `mp_black_water_canal` with a loose copy of the baked files: `trigger_out_of_bounds` sets and clears `OutOfBoundsDeadTime` on enter/leave, `trigger_hurt` kills a pilot placed in the kill volume. Capture points, soundscape and indoor-area behaviour are not verified in game. `kBakeVersion` is part of the cache fingerprint.
- CTF flag spawnpoints: in game the R1 server drops them to the floor, so on `mp_glitch` the spawnpoints (BSP z 144) report z 2.03, not the hardpoint pillar height (z 128 + 16). No height correction beyond the lift above is applied.
- A loose `<gamedir>/maps/graphs/<map>.ain` always wins over an `.ain.r2patch` package, because R1 files are consulted first.

## Background test mode

Agent and CI game windows must not disturb the person using the machine. Setting the environment variable `R1DELTA_BACKGROUND=1` (anything but `0`) or passing `-r1delta_background` turns on a mode that is never active otherwise, so normal players and hand launches are unchanged. `.build\run-in-r2.ps1` sets the variable for every launch it starts and adds `+fps_max 60 -nomessagebox` to the game arguments; a hand-launched agent window needs only the variable or the switch. The code is `engine/core/background_mode.cpp`.

- **Focus and input.** user32 hooks (MinHook, installed with the other early hooks) make `SetForegroundWindow`, `BringWindowToTop`, `SetActiveWindow`, `SetFocus`, `SwitchToThisWindow`, `ClipCursor`, `SetCursorPos`, `SetCapture` and `mouse_event` do nothing, make `SendInput` fail, make `RegisterRawInputDevices` report success without registering (no raw mouse input ever arrives), strip `WS_EX_TOPMOST`/`HWND_TOPMOST` and add `WS_EX_NOACTIVATE`/`SWP_NOACTIVATE` in `CreateWindowEx`, `SetWindowLong(Ptr)` and `SetWindowPos`, and map every `ShowWindow`, `ShowWindowAsync` and `SetWindowPlacement` show command to a non-activating one. `r1d_background_selftest hooks` reports how many are patched (26 of 26 including the message-box hooks).
- **Window placement: off-screen by default.** The window is created at (-32000,-32000) and shown with `SW_SHOWNOACTIVATE`. It keeps its full 1920x1080 size, renders and ticks at 60 fps, `screenshot` works and a `PrintWindow` client grab returns the real frame. `R1DELTA_BACKGROUND_WINDOW=minimized` selects `SW_SHOWMINNOACTIVE` instead; it also renders at 60 fps and the engine `screenshot` works, but a minimized window has a 0x0 client area (a `PrintWindow` grab only gets the 160x28 title bar), and creating the window already minimized crashes graphics initialisation (an allocation fails in the first swapchain-sized buffer), so only the show command is mapped, never the creation style.
- **60 fps.** The command line gets `+fps_max 60 +mat_vsync 0` and a watchdog thread re-applies `fps_max 60` and `mat_vsync 0` every second, so cfg files cannot override them. The engine throttles itself to about 20 fps (a 50 ms sleep per frame) while it believes it is not the active app, which a background window always is; the same thread therefore posts `WM_ACTIVATEAPP` (active) to the game's windows twice a second. Measured with a client script frame counter: 19.4 fps without it, 59.3 to 60 fps with it.
- **Crashes and message boxes.** The crash log is still written to `crashes`, but `notepad.exe` is not started and the crash sounds are not played. `MessageBoxA/W/ExA/ExW` log caption and text (console and debugger output) and return at once (`IDOK`; `IDYES` for yes/no and yes/no/cancel; `IDCANCEL` for retry/cancel; `IDIGNORE` for abort/retry/ignore). `-nomessagebox` has the same suppression in every mode, background or not. `r1d_background_selftest messagebox` and `crash` exercise both; the command is registered only in background mode.
- **Engine switches.** The command line also gets `-nosound -nomouse +cl_mouseenable 0 +cl_mouselook 0` unless already present. Verified on this engine: `-nosound` is honoured (neither `XAudio2_6.dll` nor `MMDevApi.dll` is loaded, which a normal client does load, and map load, spawning and the game state still progress). `-nomouse` cannot be observed from outside; the real guarantees are the hooks above. `cl_mouseenable` and `cl_mouselook` exist but did not change from 1 when set at run time (`cl_mouselook` is flagged not-while-connected), so they are only a best effort; `engine_no_focus_sleep`, `host_framecount`, `snd_mute_losefocus` and `volume` do not exist in this engine.

**Automatic for agent roots.** An empty file `r1delta_background.flag` next to the game executable also turns the mode on, so a launch from an agent root is a background launch whatever script started it and whether or not it sets the environment variable. `.build\r2-root.ps1` creates the flag for the four agent roots (`r2-provider`, `r2-texlib`, `r2-shader`, `r2-lead`) on `-Create`, `-Reset`, `-Repair` and `-Stage`, and never for the template `r2dev` or the user's `S:\game\r2`. Only the executable's directory is checked; the working directory (`C:\whatever` for the runner) is shared and is deliberately not consulted. However the mode is enabled, `-nosound` is applied (no audio DLL is loaded) unless `R1DELTA_BACKGROUND_SOUND=1` is set. A hand-staged root gets the flag by running `-Stage` once, or by creating the empty file.

Evidence for these results (mp_glitch from `S:\game\r2-provider`): the foreground window and its process never became the game's across a full run, the window was never topmost, and the notepad process list did not change on a forced crash.

`pvs_extraCull` on converted maps (interim fix, default ON): the CORE `cfg/autoexec_delta.cfg` sets `pvs_extraCull 1` (engine default 0), which culls whole world meshes of converted R2 maps (the glass roof over the mp_eden courtyard pad vanished; occluder lumps and ref boxes are not the cause; `pvs_extraCull 0` at runtime restores it). `ApplyR2PvsExtraCullPolicy` in `engine/net/networking.cpp` runs at every client signon state change: while an allowlisted R2 map is the active map and the cvar is nonzero it remembers the user's value and issues `pvs_extraCull 0` (one console command, nothing per frame; costs the fps benefit of extraCull on converted maps); when a stock R1 map becomes active it restores the remembered value (verified on mp_eden -> mp_box -> mp_eden). `R1DELTA_R2PORT_KEEP_PVS_EXTRACULL=1` keeps the user's value. To be removed when a converter-side fix is proven. The CORE config and the user's cfg are not edited.
